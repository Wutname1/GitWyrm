## VS Code settings were being refused outright (`8fbff62`)

Found by reading rather than by an audit: `set_path` gated on
`serde_json::from_str`, strict JSON. **VS Code's `settings.json` is JSONC** --
comments and trailing commas are ordinary, and VS Code writes them itself.

Checked against this machine's real file: it fails strict parsing at line 7,
on a trailing comma VS Code put there. So copying a connector into Copilot
was refused, with `"source is not valid JSON: expected value at line 7
column 4"` -- jargon, and it blames a file the application reads happily.

The machinery underneath never needed that gate. A probe (removed before
commit) ran the splicer directly against the real shape: trailing comma
preserved, the unrelated `[lua]` block untouched, the new entry correctly
placed. Only the gate rejected it. The check is now structural -- a top-level
object whose braces balance -- which still refuses a truncated file while
accepting one the destination reads.

## Three ways to break someone's settings file (`8fbff62`)

From the `json_patch`/`toml_patch` audit, which confirmed its findings **by
running the real code**, not by reading it. All three share a worst case: the
file comes back unparseable, so the application loses every setting in it.

1. **An unescaped key.** `format!("\"{key}\": ...")` interpolated the key
   raw. Connector names come verbatim from the source application and are
   never validated, so one containing a quote or backslash produced a broken
   file. Only the *last* path segment hit this branch, which is why it
   survived -- segments built through `pretty_print` were escaped correctly.
2. **Control characters dropped.** The hand-rolled escaper handled five
   characters and passed everything else through, including the control
   characters JSON forbids in a string. The character was lost *and* the file
   broken. Replaced with `serde_json::to_string`, which is correct by
   construction and needs no maintaining.
3. **A brace inside a string treated as the document root.** `source.find('{')`
   could land inside a string literal, so `"{}"` -- valid JSON, a string --
   was spliced into and returned as `Ok`. Now anchored to the first
   non-whitespace byte.

**The existing tests caught a mistake of mine mid-fix**: routing the key
through a function that already adds quotes, into a format string that also
added them. Three tests failed immediately.

## A finding I disproved by running it

The `plan.rs` audit reported, as its highest-severity item, that
`tempfile::persist` calls `SetFileAttributesW(FILE_ATTRIBUTE_NORMAL)` before
`MoveFileExW`, so a user who marks their config file read-only has that
protection silently cleared by every write. It cited the `tempfile` source and
flagged itself as needing confirmation.

Reproduced the exact sequence against a real read-only file:

```
move succeeded: False (0 would mean refused)
after : A    R    ...target.json
content: {"a":1}
```

`MoveFileExW` with `REPLACE_EXISTING` is **refused** against a read-only
target. Clearing the attribute makes the same move succeed, confirming that
was the blocker. So GitWyrm refuses to overwrite a protected config file --
the protection works, and the reported behaviour does not occur.

That is the third audit claim in four passes overturned by verification.

## Reported, verified, not fixed

From the two audits, recorded so the next pass judges rather than re-derives:

- **`toml_patch` normalises CRLF to LF and strips a BOM** across the whole
  file. `json_patch` handles both correctly and has a test pinning it; the
  TOML side has neither. Real, and directly contradicts its own module doc.
  Left because it is a separate file with its own shape of fix.
- **Key matching compares raw source bytes**, so a source key written
  `"we\"ird"` never matches the path `we"ird` -- an update silently becomes an
  insert, creating a duplicate, and `remove_path` returns `Ok` having removed
  nothing.
- **With duplicate keys, the patch writes the first and readers take the
  last**, so the write reports success and changes nothing the application
  observes.
- **`plan.rs`: a symlinked destination** is replaced by a regular file, so a
  dotfile-manager setup silently detaches and Undo cannot restore the link.
- **`plan.rs`: raw OS error text** reaches the user for any non-`NotFound`
  read failure ("Access is denied. (os error 5)").

`plan.rs`'s core was otherwise verified sound: atomicity is genuine (temp file
in the destination's own parent, `sync_all` before rename, no litter on
failure), the hash gate cannot be bypassed, backups key on a UUID so cannot
collide, and the receipt is written before the destination so a receipt
failure cannot strand a changed file.

## Note on method

**Two audits, one disproved finding, one found by hand.** The JSONC defect --
the one with the widest blast radius, since it blocked Copilot writes for
anyone whose settings file has a comma out of place -- came from reading the
gate and testing it against a real file, not from either commissioned audit.
The audits found the corruption bugs, which reading would not have found.

The pattern worth keeping: **commission the audit, then verify every finding
before acting, and keep reading yourself.** Neither source is sufficient.
