## Failure messages nobody outside the code could use (`a97a5b4`)

`ApplyWriteError`'s variants are developer text -- "could not rename temp file
into place", "could not flush temp file", "could not write receipt" -- and
`apply_copy_at` put `e.to_string()` straight into the dialog. Traced to the

open in another program produced

> Copilot could not be updated: could not rename temp file into place: Access

Three layers of jargon, none of which say the thing that matters -- the
settings were not changed.

`plain()` now does that, following `SkillCopyError::plain` next door. The four

same treatment, and its wrapped-write variant reuses the write's own sentence
rather than inventing a second.

## A settings file that is a shortcut (`617cfe0`)

The last pass-56 finding, and the one flagged as needing a decision.

`read_current` uses `fs::read`, which follows a link -- so the hash gate, the
backup and the merge base all describe the file the link points at. But
`temp.persist(path)` renames over the **link**, replacing it with an ordinary
file and leaving the real one stale. GitWyrm reads one file and writes
another. Undo has the same asymmetry, so the link is destroyed twice and
restored never.

### The debate, and a factual disagreement I settled myself

Two agents argued write-through-the-link against refuse-it, and they
contradicted each other on atomicity -- the crux.

**The write-through side was right on the facts.** `write_atomic_bytes`
derives both the temp directory and the rename target from the same `path`,
so resolving once moves them together and the same-volume rule holds *by
construction*. The refuse side's cross-volume objection describes the naive
half-fix -- resolve the target, leave the temp beside the link -- which nobody
proposed. I verified this by reading the function rather than taking either
account.

**It lost anyway, on consent.** Its own weakness statement concedes the
receipt would record the link's path while the bytes land elsewhere. Writing
to a path the preview never showed is precisely what "nothing lands
automatically, the user decides" forbids, whatever its atomicity properties.

**And the refuse side had the better precedent.** `skill_write.rs` -- the
sibling module, fixed five passes ago -- already refuses a folder it cannot
copy faithfully, in the authors' own words: *"Refusing costs the person one
copy; dropping costs them a file they never agreed to lose."* The link is
exactly such a thing: no backup or receipt records that it existed, so
"undo can always get back to the exact previous bytes" is true of the bytes
and false of the setup.

Refused, with a sentence naming the file to change instead.

### Reachability, stated honestly

No symlinked config exists on this machine (checked all four client paths),
so unlike the JSONC defect two passes ago I have **no local proof this is
reachable**. It is fixed on the strength of the mechanism and the precedent,
not on a demonstration. Recorded so nobody later reads it as verified in the
field.

## Note on method

**A debate can be won by the side that is wrong on the facts.** The
write-through argument was technically correct about atomicity and I confirmed
it; the refusal was still right, because the question was never really
technical. Checking the disputed fact was still worth it -- it is why the
commit message says writing through was a real alternative rather than
dismissing it, and why the Q&A records that the safety objection was
unfounded.
