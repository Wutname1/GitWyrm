## Two readers of one file, disagreeing (`90f630e`)

VS Code keeps its MCP servers under one of four possible keys depending on the
age of the settings file. `first_present_path` reads the file to find which one
it uses, so a write joins the existing map instead of starting a second one.
Its own doc comment states the stake: writing a fixed key into a file that
keeps its servers elsewhere "would add a second map the client never reads: the
write would appear to succeed and change nothing."

It parsed with **strict `serde_json`**. The write beside it goes through
`json_patch::set_path`, whose gate `check_editable` is deliberately
**JSONC-tolerant** -- and that file records exactly why: "VS Code's
`settings.json` is JSONC ... and VS Code itself writes them -- the settings
file on the machine this was found on fails strict parsing at line 7, on a
trailing comma VS Code put there."

So on an ordinary settings file the two halves of one write disagreed: the
write was accepted, the detection was not, and the fallback fired. A connector
went to `mcp.servers` while the file's servers sat under `servers`. Reported
as success; invisible to Copilot.

The fix is `json_patch::path_is_object` -- the same walk `set_path` performs,
stopping short of writing. Detection and write now agree by construction rather
than by coincidence, including on the two things this module already learned
matter: escaped keys, and taking the **last** of a duplicated key the way every
JSON reader does.

`unwrap_or` also became `?`. A file that cannot be read is not a file with no
map in it, and folding those together is how a default gets written on the
strength of a parse error.

## A test of mine that proved nothing, removed

The refusal came with a test asserting an unreadable file is not written to on
a guess. It passed. It also passed with the refusal removed.

`path_is_object` and `set_path` both start from `check_editable`, so any
document the detector cannot read is one the write refuses moments later
anyway. The refusal is correct and cannot currently be reached, which means a
test for it measures the write's gate rather than the detector's.

Deleted, and the reasoning written where the `?` is instead -- including why
the `?` stays: if the two ever stop sharing that gate, `.ok().flatten()` would
be this same defect waiting for its opportunity.

This is the third time in this sequence a test has passed with its own fix
removed. The check that catches it is the same every time and costs a minute.

## What the debate settled

One side argued for sharing the structural walker; the other that the fallback
itself is the defect and an unreadable file should be refused rather than
guessed.

**They are not rivals, and the second side said so in its own
counter-argument:** make the detector share the writer's tolerance, so ordinary
files work, *and* stop the fallback laundering ignorance into a default. Both
shipped.

The refusal side was also right that `default_path` must keep working, and
right about why it still does: a missing file arrives as `"{}\n"`, which reads
fine and simply contains no candidate. That is knowledge, not ignorance, and it
is the case the default exists for.

## Note on method

**A module that writes into someone else's files deserves a pass of its own.**
This one had none in seventy. Its reasoning is careful throughout -- the
read-only-client stance, the translate-before-write rule, the note about second
maps -- which is exactly what made the one strict parser inside it hard to see:
everything around it argues for tolerance.

**When two functions read the same bytes, check they agree.** The defect was
not a wrong rule, it was two right rules with different definitions of
readable, in the same call.
