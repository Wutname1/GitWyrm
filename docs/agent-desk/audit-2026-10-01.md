## GitWyrm could write to a file it refused to read (`30f7a11`)

Pass 70 made the **write** side tolerate JSONC, because VS Code writes comments
and trailing commas into its own settings file. The **read** side kept three
strict `serde_json::from_str` calls, and `read_generic_json_mcp` -- the one
routed to for `ClientId::VsCodeCopilot` -- was among them.

So for one ordinary settings file:

| | verdict |
|---|---|
| `json_patch` (write) | readable |
| `readers.rs` (read) | parse error |

Two consequences, both verified:

- The inventory reports a parse error where Copilot's connectors should be.
- The apply plan pushes `WarningKind::DestinationUnreadable` -- "cannot show
  what this would replace" -- so **replacing an existing connector looks
  identical to adding a new one**, on the screen where a person decides
  whether to go ahead. An earlier pass had deliberately fixed
  `unwrap_or_default()` at that site for exactly this reason; the warning it
  installed now fired on the normal case.

`strip_jsonc` normalises comments and trailing commas to spaces before
parsing, for all three JSON readers. Comments are blanked rather than deleted,
so byte offsets survive and a parse error still names the line the person has
open.

## Why stripping, and not the structural walker

The other option was to read with `json_patch`'s byte-walkers, so read and
write share one implementation. It lost on its own counter-argument, and the
argument is worth keeping: the reader's output feeds `find_secret_fields` and
`redact_for_display`. A walker that mis-judged a string boundary would
mis-split a member and could **show a secret it meant to redact**. The
stripper keeps `serde_json` as the value producer, so redaction sees exactly
what it sees today.

One agent also established a fact I had assumed the other way: `json_patch`
has twelve `in_string` sites and **zero** handling of `/`. It is comment-
*blind*, not comment-*aware* -- it preserves comments by never interpreting
them, so there was nothing to borrow.

The safety argument is settled by a test rather than by reasoning:
`stripping_never_changes_a_readable_document` asserts that for anything
`serde_json` already reads, stripping produces the same value -- URLs with
`//`, commas inside strings, escaped quotes before a `//`, a string ending in
a backslash.

## A second split, found while reading (`30f7a11`)

`read_generic_json_mcp` kept its own list of candidate keys:
`mcpServers` -> `mcp.servers` -> `github.copilot...`. The registry's writer row
declares `servers` -> `mcp.servers` -> `github.copilot...` -> `mcpServers`.

Different order, and the reader **never looked under `servers` at all** -- the
key the writer tries first. A file keeping its connectors there showed none in
the inventory while a write to that same file found them and joined that very
map. GitWyrm adding to a list it was reporting as empty.

The reader now reads the registry row. One list, one owner.

## Note on method

**Fixing one half of a split is worth a note saying which half.** Pass 70's
own audit doc says the write side was corrected; it did not ask what else read
the same file. That question was one grep, and it was sitting in the method
note that same pass wrote.

**Escaping through Python mangled Rust literals four times in this pass** --
`\\`, `\n`, `\t`, `\r` each collapsed. The fix that worked was writing the
Rust to a scratchpad file with a heredoc and splicing the file, which the
qa-log already records for PowerShell. Worth doing first for any block
containing escapes rather than after the third repair.
