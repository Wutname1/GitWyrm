# Agent Desk audit, 2026-09-24 (pass 64)

Recorded against `agent-desk-openchamber-audit-0f40fb` at `6941eb1`.

`completion.rs` has never been named in any audit doc. It decides whether a
helper actually did what it was asked to do, and its verdict decides whether
that helper's work is merged -- which makes it one of the shortest paths from
a model's own words to a change landing in the user's repository.

## A shorter name answered a longer question (`2a12eb7`)

A proposed helper carries a `CompletionCondition`. One of the three is
`ChecksPass { command }` -- "make `cargo test` pass". To decide whether a
recorded check is the one asked for, `check_matches` accepted either name
containing the other:

```rust
recorded == wanted || recorded.contains(&wanted) || wanted.contains(&recorded)
```

The third clause is loose in the wrong direction. Verified against the real
rule:

| recorded | wanted | matched |
|---|---|---|
| `cargo` | `cargo test --all-features` | yes |
| `t` | `cargo test` | yes |
| `""` | anything at all | yes |

The empty case is the sharp one: every string contains the empty string, so a
check reported with no name satisfied **every** condition.

**The name is the helper's own account.** It arrives as
`RunStep::Check { name, .. }` and is read back verbatim by
`checks_for_execution`, a plain `String` with no validation anywhere.

**And a met condition is silent.** `judge` is called from exactly one place,
`enforce_completion_condition`. `Unmet` marks the helper `Failed`, writes an
`output_summary`, and appends a plain-language note to the chat. `Met` returns
`CompletionCheck::Passed` and says nothing -- and its caller's own comment
names the stake: judged "BEFORE integration, so unmet work is not merged".

So the weakest possible name bought the strongest possible outcome. The exact
hole the module was written to close, reopened by a string rule.

Three changes:

- **Words, not substrings, and forgiving in one direction only.** Every word
  of the condition must appear as a whole word of the recorded name. Extra
  words are fine -- running more than you were asked is still doing the job.
- **An unnamed check is dropped at ingest** rather than recorded. It cannot
  answer the question either way, and `detail` on the next line was already
  dropped when blank for the same reason.
- **A differently-named check that satisfies a condition now says so** in one
  sentence. It still counts; it is no longer silent.

## A claim I checked before building on it

One sub-agent argued the token rule would *fix* `Tests (cargo test)` -- the
doc comment's own example -- on the grounds that it fails today. Ran it: it
passes today, because it contains `cargo test` as a substring.

That correction changed the fix. A naive word rule would have **broken** the
example, since its words are `(cargo` and `test)`. Trimming punctuation from
each word keeps it working. Had I taken the claim at face value I would have
shipped a regression against the one case the doc singles out, with a test
asserting the wrong thing.

## The doc claimed more than the code does (`6941eb1`)

`judge`'s comment said it "never asks the model whether it thinks it
succeeded, because a helper's own account is exactly what a condition exists
to verify."

`passed: bool` is the helper's own account too. Nothing re-runs the check --
a deliberate choice, argued on cost grounds in the module's own header. So a
helper reporting a check it never ran is believed, and hardening the *name*
does not change that.

The comment now says exactly how far the verification goes: that a report is
about the right thing, which is a smaller claim than that the check passed.
Left as a comment rather than "fixed" by re-running checks -- that decision is
already made and reasoned, and quietly reversing it in a review pass would be
the wrong way to revisit it.

## Note on method

**A competing argument's strongest concrete claim is the one most worth
running.** Both agents were substantive and both were partly right. The single
factual assertion that would have changed the shipped code -- "this case fails
today" -- took one probe to disprove. That is now twice in two passes that a
sub-agent's cited detail did not survive checking, while the *shape* of both
debates was sound.

**A comment that flatters the code is a defect with a long half-life.** This
one had been read and believed by at least me, at the start of this pass, and
would have made the next reader trust the matcher more than it deserves.

Newly noted, not acted on: **a check's `passed` is self-reported.** Re-running
it to grade a helper is explicitly declined in `completion.rs`'s header, and
that reasoning stands. But the gap between "the helper says this passed" and
"this passed" is now the widest remaining assumption in the completion path,
and it deserves a decision rather than only a comment.
