## Fixed: a copy that stopped partway left nothing (`27f298c`)

Pass 53 called this the most likely of the three to actually happen, and it
is: a file held open by the destination app is ordinary on Windows.

`apply_skill_copy` deletes the old folder, then writes the new files. A write
failing mid-loop returned through `?`, so the person was left with the old
folder gone, some new files on disk, and **no receipt** -- the backup sat in
GitWyrm's own data with nothing in the app pointing at it, and no Undo entry
to reach it by. The comment above the backup claimed a failure "still leaves
something to restore from", which was true of the bytes on disk and false of
anything the person could do about it.

`roll_back` now runs before the error returns. It is best-effort by design:
it executes while already returning a failure, and a rollback that itself
failed must not replace the real reason the copy stopped with a second, less
useful one.

With no backup, the destination did not exist before -- so removing the
half-written folder *is* the restore. Left alone it would look like a working
skill.

**The test drives a real failure, not a simulated one.** The source holds a
file named `references` and a file at `references/api.md`; those cannot both
exist at the destination, so the second write fails on every platform with no
privilege needed, after the old folder has already been deleted -- exactly the
window that used to lose it. My first attempt tested `roll_back` directly and
left dead exploratory code in the test; that was replaced.

## Fixed: the size cap read the file it was about to refuse (`60f595f`)

`collect` read each file fully into memory and only then compared against
`MAX_TOTAL_BYTES`. The cap's own doc says the bounds exist so a mistaken
folder "is refused quickly instead of read into memory" -- so the comment
described the opposite of the code. A repository checked out inside a skills
directory, the case the comment names, was loaded a file at a time before
being turned away.

Size now comes from the directory entry, before anything is opened.

### A reported bug that did not exist

The same audit reported the file-count check as off by one: `out.len() >=
MAX_FILES` compares before the insert, so "201 files are actually accepted".

I wrote the fix, then reverted it to watch the test fail -- and it passed.
`out.len() >= MAX_FILES` and `out.len() + 1 > MAX_FILES` are the same
condition. **The reported bug never existed**, and without the revert step I
would have shipped a comment asserting a defect that was never there.

The condition is kept in the `+ 1 >` form because that is what it means, with
a note saying a review misread it and it is not off by one. Two tests pin the
boundary from both sides.

### A test that pins less than it appears to

`one_oversized_file_is_refused_by_its_recorded_size` passes with the fix and
without it -- reading an 8 MB sparse file succeeds, and the cap then refuses
it either way. The fix that matters is about *memory*, which no unit test
here can observe.

Rather than delete the test or let it imply more than it shows, its doc says
so outright: it pins the refusal, not the reason. Pass 53 found a test of mine
that could never have caught anything; this is the adjacent failure -- a test
that catches something, but not the thing its name suggests.

and the UI copy. That is a pass of its own, not a tail-end change here.

## Note on method

Two passes running, the revert step has caught something the tests alone would
not have:

- Pass 53: a test that could never run here, passing while proving nothing.
- Pass 54: a reported defect that did not exist, which I had already written a
  fix and an explanatory comment for.

The second is the more uncomfortable one. The audit was specific, plausible,
and cited the line -- and I was one commit away from documenting a bug into
existence. **Reverting the fix to watch the test fail is not a formality about
the test; it is the check on whether the finding was real.**
