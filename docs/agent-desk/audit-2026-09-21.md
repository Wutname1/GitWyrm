## Twelve confirm dialogs that could not show their own progress (`333a99c`)

`ConfirmDialog` closes itself after `onConfirm` unless the caller passes
`keepOpenOnConfirm`:

```tsx
onSubmit={() => { onConfirm(); if (!keepOpenOnConfirm) onOpenChange(false) }}
```

So a `pending` prop without `keepOpenOnConfirm` is **dead code**. The dialog is
gone before the value it would render becomes true. The button is never
disabled, the label is never seen.

Twelve dialogs were in that state, across the whole app rather than this
workspace: deleting a file, restoring a file, deleting a branch, removing a
tag from the server, removing a worktree, deleting the branch behind it,
matching a submodule, removing a submodule, archiving and deleting a spec
change from two places, asking Dependabot, deleting a chat, and throwing away
an agent's work.

Every one of them had been written with the protection in mind -- eleven
passed `pendingLabel` ("Deleting…", "Removing…", "Archiving…") and a `pending`
expression. None of it could reach the screen.

Two consequences, both Rule #1:

- A slow action showed **nothing at all**. Removing a worktree with a dirty
  tree is not instant, and the dialog vanished the moment it was confirmed.
- The confirm button was never disabled, so a double-click sent the action
  twice. That is where pass 60's report came from: the second delete returns
  `failed` because the thing is already gone, and a red error is shown for an
  action that worked.

**Nineteen other dialogs already pass `keepOpenOnConfirm`** -- including two
in `LeftPanel.tsx` and three in `GithubContextPanel.tsx`, files that also hold
offenders. So this was an omission repeated by hand, not a decision.

Each fixed dialog now closes from its own mutation's `onSettled` rather than
`onSuccess`, so a throw closes it too instead of stranding it open behind an
error toast. `DeskActionRail` needed that specifically: its five success
branches each closed the dialog themselves, and its `onError` did not.

## The guard, and the guard's own bug

`src/lib/confirmPendingContract.test.ts` fails when a `ConfirmDialog` passes
`pending` without `keepOpenOnConfirm`. Source-scanning, in the style this repo
already uses for `hookOrderContract` and `eventPayloadContract`, because
`vitest.config.ts` deliberately excludes components.

**Its first version was wrong, and wrong in the direction that matters.** It
took each element as the text from `<ConfirmDialog` to the first `/>`. These
dialogs carry rich JSX `description` props holding fragments, `<span/>`s and
`{/* ... */}` comments -- all of which contain `/>` sequences. The cut landed
inside the description, before the props being checked.

So it reported one offender and passed the two dialogs I had *just fixed by
hand*, for the wrong reason. It now walks `{`/`}` depth and accepts a `/>`
only at depth zero. That version found ten more.

## Note on method

**A guard that passes is not evidence until it has failed.** The revert check
is what exposed this: I removed `keepOpenOnConfirm` from a fixed dialog,
expected the test to name that file, and it stayed green. Without that step I
would have committed a fix for two dialogs plus a test that certified the
other ten as clean -- worse than no test, because the next person would trust
it.

This is the seventh time this pass sequence has caught something by reverting
the fix and watching the test fail. It is the only habit here that has never
produced a false result.

**A finding logged as cosmetic deserves one look before it is closed.** Pass
60 recorded this as "narrow window, cosmetic, and the fix belongs with the
dialog rather than the hook" -- accurate about where the fix belonged, wrong
about the size. The mechanism it named (a missing gate) was general, and the
question "where else is this?" was one grep away.
