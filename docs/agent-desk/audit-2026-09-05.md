## Correction: F1 was already closed before it was written

The competitive audit's F1 says the Copilot registry "selects home-relative
`.config/Code/User/settings.json` and repository `.vscode/settings.json`" and
"misses" VS Code's documented `mcp.json` paths.

Those are still the *file* paths, but the finding's conclusion does not hold:
`registry.rs` gives Copilot a `JsonMcpMapFirstPresent` writer whose candidates
are `servers`, `mcp.servers`, `github.copilot.chat.mcp.servers` and
`mcpServers`, defaulting a fresh file to `mcp.servers` -- the modern key VS
Code documents. It follows whichever shape the file already uses rather than
picking one, which is the behaviour F1 asks for. This landed in `4296bd9` and
`a296d75`, after the snapshot the audit read.

Recorded here because two documents now describe this as open, and the next
reader would otherwise spend the time twice. The *ownership* half of F1 --
OpenChamber reading merged OpenCode configuration rather than owning its own
-- is untouched and remains open.

## Resolved this pass

### F2 -- copying a connector did not translate its shape (`03fdefc`)

Confirmed real and the most serious of the three, because it fails silently.
Readers store every client-specific field verbatim in `RawItem::extra`
(`readers.rs:109,131,159,184`) and `writers::build_new_content` wrapped those
same fields in the destination's map. Only the outer key changed.

Verified against the reference implementation rather than documentation:
`F:\openchamber\packages\web\server\lib\opencode\mcp.js:165-268` shows
OpenCode requires `type`, a `command` **array**, `environment` (not `env`) and
`enabled`, and strips `url`/`headers` from a local entry. A Claude connector
(`command: "npx"`, `args: [...]`, `env: {...}`) copied into OpenCode therefore
arrived in a shape OpenCode parses and ignores: it appears in the config and
never starts, with no error, because the file write genuinely succeeded.

`agent_config/connector.rs` now parses a source entry into a `Connector` with
no client in it, and re-serialises it per destination `Dialect`. The dialect
is derived from `ClientId` exhaustively, so a new client cannot inherit a
shape nobody checked. Fields outside the model survive the round trip and are
reported to the person in the preview rather than transplanted quietly, and an
entry whose transport is unrecognised says so instead of being presented as
understood.

13 tests, including a round-trip that must return the original shape -- absent
that, a connector degrades slightly on every copy. One existing test
(`opencode_writer_merges_into_mcp`) asserted the old untranslated output and
was updated; it had been pinning the defect.

### F3 -- a false claim about another product (`9843880`)

`skill_copy_preview` told the person that the destination "does not keep
skills, so there is nowhere to copy this." GitWyrm had not checked. It knows
where Claude Code keeps skills (`skills.rs:205-229`) and nowhere else, so the
sentence asserted a capability limit of another product from GitWyrm's own
missing support, and told the reader to stop looking rather than that support
is absent here.

Now says GitWyrm cannot copy skills there yet. A missing home directory was
reaching the same branch and is now reported as the different problem it is.
The test walks every client GitWyrm cannot copy skills to and fails if the
wording blames the client again; it was verified to fail against the old
string before being kept.

The coverage half of F3 -- adding real skill destinations for other clients --
is deliberately not attempted here. It needs a verified install of each
client, which this pass does not have.

### F6 -- pinning could report success invisibly (`1d6145b`)

Two entry points, one width rule between them. `onPinDock` resolves through
`resolveDrop` with `rightZoneUnavailable`; `onPin` (the pane popover's Pin)
called `openDock` directly and toasted "pinned" unconditionally. Below
`RIGHT_DOCK_UNSAFE_WIDTH_PX` (900) a right dock resolves to
`popover-fallback` and is not rendered pinned, so that path reported success
for a panel the person could not see -- a direct Rule #1 violation.

`resolvePin` is the shared decision. It is deliberately not `resolveDrop`:
that function rejects when no dock exists, which is right for a move and wrong
for a pin, since pinning the first panel is exactly the case where nothing is
pinned. Verified to fail against the old behaviour before being kept.

### F5 -- two controls, two answers about which AI is active (`444f302`)

Settled by two opposing agents arguing the alternatives against the vision;
recorded as Q191. The losing option -- make the titlebar chip mirror the
active chat -- was rejected on evidence the argument itself surfaced: the chip
is not a stowaway. `useAiSelection.ready` folds `aiEnabled` into commit-message
generation, the split dialog, conflict resolution, spec drafting and the Ask
tab, and `ResultReviewPanel.tsx:123-144` runs Agent Desk's own "send this
result back to the spec" on *this* provider, not the chat's. Mirroring the
chat would have stranded a switch that governs seven surfaces, and in split
view a chip following focus is either wrong in one pane or mutating under the
person as they click.

So the wiring was already correct and the *words* were the defect. The chip
described itself as "the single trust anchor for every AI action in this
window" while a chat below it could run on a different provider entirely, or
run at all with the chip reading "off". It now takes a `scope`, calls itself
writing help in Agent Desk, points every tooltip at the per-chat control, and
says plainly that switching off leaves chats alone. Spec Desk, which genuinely
has one AI, is unchanged.

The strings live in `lib/aiChipScope.ts` so they are testable without a
component renderer -- this repo has no testing-library setup and all 79 test
files are pure logic, so adding one for four strings was not worth the
dependency.

## Note on method

Three of the four fixes above were verified by reverting the fix and watching
the new test fail with the expected message, then restoring it. Q142 records
that both new detectors in an earlier pass were silently wrong at first and
only reverting the real defect proved them. That step is cheap and has now
caught enough to be worth doing every time.
