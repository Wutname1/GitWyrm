## A client reported absent while its contents were listed (`e867466`)

`detect_clients` answers "is this client here?" by testing whether any declared
**config file** exists. Connectors are read from those same files, so for them
the two answers agree by construction.

**Skills are not.** They are scanned out of `<client>/skills` folders, which
appear nowhere in the declared config paths. So someone with
`~/.claude/skills/foo/SKILL.md` and no `~/.claude/settings.json` gets skills
listed for a client whose row simultaneously reads `ClientNotDetected` --
documented as "Client not detected on this machine at all."

The rule that prevents this was already in `client_state`: the branch where the
client **has** the item never consults `detected`. But it held by accident, and
no test could tell -- every existing case used connectors, where the two
answers cannot disagree. It is now stated and checked in both directions.

## What the debate settled

Both agents agreed on the core: a read item is direct evidence, and outranks a
config-file heuristic. They split on whether detection should also widen to
count skills folders.

Widening lost on what `present` drives. It is not decorative: `ClientNotDetected`
produces a plan warning with `write_supported: false`, and `isEligibleDestination`
returns false for it -- so it genuinely blocks a client from being a copy
destination. A skills folder can be left behind by an uninstall or copied in by
hand, and treating one as proof of installation would offer a **connector**
destination whose config file really is absent. That trades a visible
contradiction for a quiet one.

The losing side's surviving objection was acted on: the Detected-apps tab said
"Not found on this machine" -- a claim about the app -- when what was checked is
whether its settings file is there. It now says so.

## Note on method

**An accidental invariant is worth pinning even when it is already correct.**
Nothing here was broken in the code; the rule was right and unstated, and the
one input shape that could expose it was untested. A pass that only fixed
broken things would have walked past it.

**A negative path result is not automatically a finding.** Two declared paths
do not exist on this machine, and both are honest absences. Pass 73's success
made it tempting to read every miss as another bug.
