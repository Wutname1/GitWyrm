## A team offered to a chat that can only work alone (`bdd8403`)

The new-chat screen asks two questions in adjacent sections. "How much can it
do?" (Ask/Plan/Auto) respects a `canWrite` prop, with a comment recording that
it was fixed for exactly this: offering choices that "lit up a choice that
would never take effect" and put the screen "in disagreement with the pills
directly beneath it".

"How many agents?" sits eight lines below and blocked nothing at all.

**Helpers do not exist in Ask.** `agent_desk.rs` adds the instruction that lets
a lead hand work out only for Plan and Auto; for Ask it is `None`.
`ExecutionPolicy::resolve` does not clamp `team` against the intent, so
`ExecutionTeam::Lead` really does reach the backend -- and then produces
nothing. `MODE_NOTES.Ask` already says "Read and answer only; **no helpers**"
on the card directly above.

**And it was the default, not a corner.** `SessionComposer` seeds
`team` to `'helpers'`. Every read-only chat -- Explain, Review, Summarize,
Ask -- opened with a team selected. The line above the message box read "A
lead agent, up to 3 helpers" for a run that would have neither.

Three controls said it; all three now ask the mode: the landing card, that
composer line, and `TeamShapeControl`'s popover. The popover's own description
had already named the truth without noticing -- "Plan lets you approve the
split first; Auto starts it when useful" lists two modes and not the third.

Nothing is silently changed. A selected team stays selected and renders
blocked, so switching to Ask does not quietly discard a choice; switching back
to Plan or Auto restores it.

## The predicate, and why `canWrite` lost

Both sub-agents were asked to defend a different condition, and the
`canWrite` side **conceded its own predicate in its counter-argument**: the
backend gates on mode, not on write permission, so `canWrite` fixes the
read-only case and leaves a perfectly writable chat sitting in Ask still
lying. It also noted that preferring `canWrite` because it is "the prop
already threaded" is convenience reasoning rather than correctness reasoning.

`isTeamBlocked(mode)` covers both: a read-only chat is included because
`isModeBlocked` already pins it to Ask. A test asserts that relationship
directly rather than assuming it.

## A stale comment that would have misled the next reader (`3cae9c9`)

`vitest.config.ts` says its scope "is `src/lib`", and every previous pass --
including several of mine -- has quoted that as a constraint. Its `include` is
actually `src/**/*.test.ts`, and **ten test files already live outside
`src/lib`** and all run.

The consequence is not hypothetical: a colocated test written next to the
thing it tests would have been assumed dead by whoever read that comment.
Corrected to say what the pattern does, and where the real line is -- a
`.test.tsx` is not matched, which is what actually separates covered logic
from uncovered rendering.

## Note on method

**A fix applied to one of two adjacent controls is the signature to grep for.**
The mode section carried a comment describing this exact defect, written when
it was fixed there. The same sentence described its neighbour, unchanged,
eight lines away. When a comment explains why a control was corrected, the
question worth asking is which sibling was in the same state and did not get
the same treatment.

**A constraint everyone repeats is worth checking once.** "Tests only cover
`src/lib`" shaped decisions in at least three earlier passes, including
choices to move logic into `src/lib` so it could be tested. Those moves were
independently good, but the reason given for them was not true.
