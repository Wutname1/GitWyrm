## A description long enough to write is long enough to lose (`0748cd7`)

`pullRequestUrlWithDraft` puts the drafted title and body into the host's
compare-page query string. That is the whole mechanism, and it is a good one:
GitWyrm never pushes and never calls a host write API, so the person still
presses the host's own button.

But a URL has a ceiling, and nothing checked it. Measured:

| description | resulting URL |
|---|---|
| 214 chars | 329 |
| 856 chars | 1,031 |
| **2,140 chars** | **2,435 -- over the limit** |

Windows opens the page through `ShellExecute`, which stops accepting a URL
near 2048 characters, and Windows is the platform GitWyrm ships an installer
for. The dialog offers an **eight-row textarea**. Ten short paragraphs is an
ordinary pull request description, not an extreme one.

**And the failure took the writing with it.** `PullRequestDraftDialog` called
`onOpen(url)` and `onOpenChange(false)` on the next line, synchronously, while
the open is async. The dialog's state is reseeded from props every time it
opens, and there is no draft persistence anywhere. So on *any* failure the
person's edited title and description were gone, and what they got was a toast
saying the page could not be opened.

Three changes:

- The dialog holds open until the open resolves, with an "Opening…" button,
  and closes only on success. That covers every failure, not only the one
  measured -- no browser, an opener error, a host address that will not parse.
- `pullRequestUrlWithDraft` now returns `{ url, bodyFitsInLink }`. Over the
  limit, the link carries the title only and the description goes to the
  clipboard with a sentence saying to paste it.
- **The description is never shortened.** A clipped description looks complete
  on the host's page; the person publishes half a pull request believing it
  whole. All-or-nothing, with the clipboard as the other route.
- The "Copy the description" button is no longer gated behind `updating`. It
  was already the answer to one way the text cannot travel in a link; it is
  the answer to the others too.

## What the debate settled

Both sub-agents were asked to argue opposite fixes, and **both independently
concluded "ship both"** in their own counter-arguments -- one saying the
lifecycle fix is the one to keep if only one ships, the other saying the
length case still needs to be named or the person cannot tell why it failed.
That agreement is the verdict: the lifecycle fix generalises, the length
guard explains.

The `keepOpenOnConfirm` precedent from pass 61 was cited by both. It does not
literally apply -- this is a raw `Dialog`, not `ConfirmDialog` -- but the
principle is the same one, and implementing it by hand here is what the
component needed.

## A defect I introduced and caught

The first version of the guard reported `bodyFitsInLink: true` for an
**unrecognised host**. `buildUrl` returns the plain compare URL untouched for
a host it does not know, so the description never travelled at all -- and my
guard, seeing a short URL, said it had. The caller would then skip the
clipboard, and the description would be lost exactly the way the fix was
written to prevent.

Found by asking what the function returns for each branch rather than only
for the branch being changed. Now guarded and tested, and the test fails
without it.

## Note on method

**A revert check can leave a comment orphaned.** Undoing the unknown-host
guard removed its code and left its four-line explanation sitting above an
unrelated `if`. Harmless here because the restore was immediate, but a
reverted-and-forgotten comment is a false claim in the source, which is the
same class of defect pass 64 fixed in `completion.rs`. Worth reading the
region back after a revert, not only the test result.
