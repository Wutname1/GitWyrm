## Codex skills, from a real install (`1546596`)

Pass 52 added OpenCode by reading OpenCode's own loader. Codex had no such
source available, but this machine has a real Codex install --
`~/.codex/skills/mobile-design/SKILL.md`, with the frontmatter GitWyrm's
reader expects. That is evidence, not documentation.

**Verified end to end, not just by unit test.** A temporary probe ran
GitWyrm's own `skill_dirs` + `read_skills_at` against the real install and
found the actual skill:

```
PROBE dir=C:\Users\jerem\.codex\skills found=1
PROBE   identity=mobile-design display=mobile-design
```

The probe was removed before commit and the tree checked clean -- pass 49
recorded a sub-agent leaving exactly this kind of scaffolding behind, and it
was committed by mistake.

**Deliberately narrower than it could have been.** Codex gets one location.
A `.codex` folder at a project root is real (it holds `config.toml`,
`agents`, `hooks.json`), but nothing observed puts skills in one, and a
guessed second path would scan a folder nobody writes to and report no
project skills -- indistinguishable from really having none. **VS Code
Copilot is still absent**: no skills folder exists on a machine that has
Copilot installed, so GitWyrm keeps saying it cannot copy skills there rather
than guessing a location.

This is the same discipline pass 45 established when it fixed the *wording*
of this limit. The limit is lifted where there is evidence and kept where
there is not.

## New ground: the skill copy write path (`b5df544`)

`skill_write.rs` -- 690 lines, 12 tests, never audited in 52 passes. It just
became a real user path: until pass 52 only Claude Code was a skill
destination, so this code could barely be exercised. **It writes into folders
owned by other applications**, which makes a bug here damage a user's actual
Claude/Codex/OpenCode setup rather than GitWyrm's own data.

Two severe findings, sharing one root cause: **backup and restore reused the
policy for *reading* a source skill.**

### The backup was lossy, and the original was deleted anyway

`copy_tree` backed the destination up via `read_skill_tree`, which skips
symlinks (`skill_write.rs:158`) -- correct for a folder the person chose to
copy, wrong for one they did not. The backup reported success having quietly
omitted the link, and the caller then deleted the original unconditionally.
Undo restored a folder that was not what had been there, with nothing said at
any point.

The comment above that call claimed the backup left "something to restore
from", and the module header claimed "Undo restores exactly what was there".
Both were false for any destination containing a symlink.

Now a folder that cannot be copied faithfully is refused up front and left
untouched. Refusing costs one copy; dropping costs a file nobody agreed to
lose.

### Undo deleted the copy before checking it could restore

`undo_skill_copy` ran `remove_dir_all` on the destination and only then read
the backup. A backup that had gone -- cleared app data, a hand-deleted
folder, a file quarantined by antivirus -- left the user with **neither**
version, and the error read "That skill's folder is not there any more",
which reads as nothing having happened.

Now the backup is read first and the destination is only touched once the
restore is known to be possible.

### A test that could never have caught anything

Worth recording on its own. My first symlink test was end-to-end and
self-skipping: creating a symlink needs a privilege this session lacks, so it
returned early and **passed with the fix removed**. That is precisely the
Q142 pattern -- a guard that has never caught its own instance.

Replaced with a direct test of the check itself, needing no privilege, which
was verified to fail against a deliberately broken detector. The end-to-end
symlink case is kept but is now clearly labelled as running only where a link
can actually be created.

## Reported, verified, and not acted on

Three further findings from the same audit, recorded so the next pass judges
rather than re-derives:

- **A partial copy leaves no receipt**, so a write that fails halfway (a file
  locked by the destination app is ordinary on Windows) leaves a half-written
  skill, a backup on disk, and no Undo entry pointing at it. Real, and the
  most likely of the three to occur. Not fixed here because the fix is a
  rollback-or-save-receipt decision that deserves its own pass.
- **The size caps are checked one file too late**, so a huge file is read
  fully into memory before being rejected -- and the doc comment claims the
  opposite. Correctness debt with a false premise attached.
- **`folder_digest` inherits the read caps**, so an oversized destination
  silently disables Undo's "you edited this" check.

**Path traversal was checked hard and is clean.** Identity comes from
`Path::file_name()`, which cannot contain a separator or be `..`;
`relative_key` and `safe_join` independently re-reject non-normal components
at write time. Belt and braces, both correct.

## Note on method

**A newly-reachable path deserves an audit even if the code is old.**
`skill_write.rs` had sat unexamined through 52 passes partly because it was
nearly unreachable -- one destination, rarely used. Adding two destinations in
the previous pass turned it into a real user path, and the audit immediately
found two ways to lose someone's files. Reachability changed; the risk changed
with it.

**A skipped test is not a passing test.** The symlink case looked green while
proving nothing. The only reason it was caught is the standing habit of
reverting the fix to watch the test fail -- which is worth more than the tests
it validates.
