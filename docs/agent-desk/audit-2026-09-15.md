## Not knowing bought permission to delete (`265524c`)

After copying a skill over an existing one, `apply_skill_copy` fingerprints
the result so Undo can refuse when the person has edited it since. That
fingerprint was recorded as `folder_digest(...).ok()` -- and `None` already
means something else: *"a receipt written before fingerprints existed"*, which
Undo deliberately treats as safe to remove rather than refusing every
historical receipt.

So a failure to fingerprint inherited that permission. Undo deleted a folder
inside another application's config directory having verified nothing, and
told the person it was put back.

### The debate, and what each side got right

Two agents argued a three-state type against leaving `Option<String>` alone.
**Both were partly right, and the useful output was the reachability
analysis.**

The leave-it-alone side traced the chain rigorously and I verified every step:
`read_skill_tree` caps the *source*, `remove_dir_all` empties the
destination, `write_tree` writes exactly that tree -- so the folder being
fingerprinted is a fresh copy of something that just cleared the caps and
cannot trip them itself. **That part is correct**, and it means the cap-based
reachability the original finding described does not exist.

The refuse side found what that misses: the fingerprint *reads the folder
after writing it*, so a file the destination app opens in that window is a
plain read failure, not a cap trip. This module's own comments already call
that lock "not a remote case" on Windows, four lines above. Narrow, but real,
and the only path to an unguarded `remove_dir_all` of an edited skill.

### Where I disagreed with both

The refuse side costed its proposal as a specta-visible enum crossing the
bindings boundary. Checking that myself: `SkillCopyReceipt` has **no**
`Serialize`/`Type` derive -- it is internal. But the *persisted* field in
`model.rs:586` does cross, so a type change there would touch on-disk receipts
and TypeScript.

So neither "cheap enum" nor "leave it entirely" was right. The distinction
belongs in the value, not the type: a `DIGEST_UNAVAILABLE` sentinel that
cannot collide with a hex hash. Nothing persisted changed shape, no bindings
regenerated, and Undo now refuses with a sentence that says what the person
can do instead ("Delete it yourself if you want it gone").

## The invariant now has a guard

The leave-it-alone argument named its own weakness precisely: the reasoning
that makes the caps unreachable *"lives in my reasoning, not in the type"*,
and holds only because replacement deletes before writing. Make replacement a
merge and the destination could grow past a cap, fingerprints would start
failing, and Undo's edit-check would silently switch off with nothing failing.

`a_replace_empties_the_destination_before_writing` pins exactly that. It is
the more valuable half of this pass: the fix addresses a narrow window, the
guard addresses the thing that would make the window wide.

## Note on method

**Neither side of a debate has to be right for it to pay.** The reachability
chain from one and the post-write race from the other were both correct and
neither was complete; the cost estimate came from checking the derives myself
rather than from either. The verdict was a third option neither proposed.

**A weakness a losing argument names is worth building against.** The guard
test here exists because the argument I mostly agreed with said plainly what
would break it. That is a better source of tests than a finding, because it
points at the future rather than the past.
