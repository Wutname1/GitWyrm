## Where this pass looked

`agentdesk/locks.rs` has 3 tests across 270 lines -- the thinnest coverage in
the module. Reading it, the code is not the risk: it is careful, and its doc
comment states the invariant plainly. The risk is that the invariant is
*delegated*. `SessionLocks` is only correct if every mutating path calls it,
and nothing checks that.

The check came out clean for sessions -- `store::write_session` has one
production call shape and every one is inside `with_session_lock`. But the same
question asked of the neighbouring file found the gap.

## Two chats imported at once, one of them forgotten (`4aa3d0f`)

The import ledger (`imports/<adapter-id>.json`) records which external chats
have already been brought in. `import_session_at` read it at
`agent_import.rs:409`, did its slow work -- reading the other tool's
conversation files, building and writing a GitWyrm session, rebuilding the
index -- then wrote **its own whole copy** of the ledger back at :476 or :523.

`agent_import_session` is `async` + `spawn_blocking`, and `ImportPicker.tsx`
calls `useImportExternalSession()` *inside* `SessionRow`, so each row owns an
independent mutation and an independent `isPending`. Two rows import
concurrently. Both read the ledger, each inserts its own entry, and the slower
writer puts back what it read at the start -- erasing the other's.

The chat itself is saved; only the record of it goes missing. That record is
the sole dedup for a first import, so the chat then looks like it was never
brought in, and importing it again builds a **second copy of the whole
conversation**. The create path's own comment already names that as the one
case that silently duplicates.

`remove_link` raced the same file from the other direction, and its caller
holds a lock keyed by *session id* while the import path was keyed by nothing
-- two different keys guarding one file, which is the same as no lock.

## Why the fix went in `import_store.rs`

Two sub-agents argued it. The reuse-`SessionLocks` case is real: `agent_graph`
already namespaces a synthetic key (`integration:{session_id}`,
`agent_graph.rs:60-79`) with a reasoned doc comment, so the precedent exists.

It lost on one fact. A caller-side adapter lock fixes the import path and
leaves `remove_link` racing, because unlink is already locked by session id and
would never contend with an adapter key. Fixing one of two writers is the
"partial fix leaves sibling paths" shape this repo has hit before.

`with_ledger_mut(root, adapter_id, f)` owns the read, the change and the write.
Everything slow stays outside it, so two imports still overlap for all the work
that actually takes time. `f` sees the ledger as it stands *now*, which is what
makes concurrent inserts merge: `sessions` is a `BTreeMap` keyed by external
session id, so two chats are two keys and both survive. There is now exactly
one production caller of `write_ledger`, inside that function.

## Three tests, and a distinction worth keeping

`two_concurrent_imports_from_one_tool_both_survive` and
`unlinking_one_chat_does_not_race_an_import_of_another` both fail with the lock
removed.

But **the revert check showed them failing for the wrong reason.** Without the
lock, on Windows, the two writers collide on the temp-file rename and fail with
"Access is denied" before either can lose an update. That is a real collision,
and it would have let these tests pass on a platform where the rename happens
to succeed while the entry still vanished.

So `the_old_read_modify_write_shape_loses_an_entry` pins the defect with no
timing involved at all: two reads of the same starting state, two writes, and
an assertion that the first entry is gone -- then the same two changes through
`with_ledger_mut`, keeping both.

## The import row said nothing while it worked (`49f851a`)

Reading a chat out of another tool opens and parses every message in it. The
Import button only dimmed. A control that dims without saying why reads as a
click that did not register, which is Rule #1's failure mode rather than its
success -- and the source panel's own refresh button, on screen beside it,
already showed a spinner and said "Checking...".

**"Continue here" had no gate at all** -- no `disabled`, no label change -- on
the one action in this list that replaces the whole view on success. A second
click landed after the screen had already changed.

A scan for the same shape across every button in `src/components` returned two
more candidates, both false positives on inspection: one tracks progress in a
separate state variable, the other shares its mutation with a button that
already shows the spinner. So this was the outlier, not a pattern, and no
contract test was added for it.

## Note on method

**A well-written module can still be the risk, if its correctness lives in its
callers.** `locks.rs` is the best-documented file in this subsystem and needed
no change. What it needed was someone to check the sentence it opens with,
which turned out to hold for sessions and not for the neighbouring ledger.

**A test that fails is not yet a test that fails for the right reason.** The
revert check is routine here by now, but this is the first pass where it showed
the new tests failing on a *different* defect than the one they name. Watching
the message, not just the red, is the part that caught it.
