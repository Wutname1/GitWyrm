## Unknown became zero, in four places at once (`3d569e0`)

`changed_paths_for_worktree` opens the agent's worktree with git2 and walks
`repo.statuses()`. Real measurement, not self-report -- which is what makes
`FilesChanged` conditions meaningfully stronger than `ChecksPass` ones.

The result build then did:

```rust
Some(p) => changed_paths_for_worktree(Path::new(p)).unwrap_or_default(),
```

`unwrap_or_default()` turns a failure to measure into an empty list, which is
byte-identical to a measured "changed nothing". The record is persisted and
becomes the authority for four separate decisions, none of which could tell
the difference:

- `ResultReviewPanel` renders **"No file changes"** -- a confident statement
  about something never checked.
- `ResultRecord::has_landable_changes` returns false, so **Keep refuses**.
  Real work in that folder became unkeepable, with the reason given as
  "nothing to keep".
- `completion.rs` fails a helper asked to change specific files and posts
  **"It was asked to change specific files, but it left no changes at all"**
  into the chat -- an accusation about the agent assembled out of GitWyrm's
  own failure to open a directory.
- `spec_return` refuses with `NothingChanged`.

**The house style was already written down, one caller away.** The same
function has a second caller in the Undo path that handles the identical
failure deliberately: `Err(_) => Some(UnexpectedPaths { modified: 1, ... })`,
with a comment saying "An unreadable worktree is still treated as touched:
the same safe-direction-to-be-wrong-in stance". One caller assumes work
exists; the other assumed it does not. Only one of those can be the rule, and
the one with the comment is the one that protects the person.

The record now carries `changed_paths_unreadable: Option<String>` --
additive, `#[serde(default)]`, following `linked_execution_ids` on the same
struct, so every saved record reads back as `None`, which is true of all of
them. A test loads a pre-field record to keep that claim checkable.

Each consumer then says the honest thing, and they do not all say the same
thing:

- The panel: what changed is unknown.
- Keep: a distinct `WorktreeUnreadable` refusal naming the folder problem and
  suggesting closing whatever is using it. `has_landable_changes` now answers
  **yes** when it could not look, so the refusal happens further in where it
  can explain itself, rather than being silently swallowed as "nothing here".
- Completion: **still Unmet** -- a condition nobody could check is not a
  condition met, and nothing should merge on a guess -- but the sentence stops
  blaming the helper.
- `spec_return`: a distinct `ChangesUnreadable`.

## What the debate turned on

Two sub-agents: refuse to build the result at all, versus record the unknown
and carry it.

Refusing is genuinely cheaper and both callers of `build_result_at` already
handle a non-`Built` outcome gracefully -- that was traced and is true. It
lost on what refusing throws away: `outcome`, `checks`, `head_oid` and
`base_oid` **were** measured successfully. Discarding all of them because one
part failed is a second unknown-becomes-nothing, one layer up.

Both agents independently identified the Undo precedent as decisive, and read
it the same way.

## Note on method

**"Unknown stays unknown" fails in clusters, not singly.** One
`unwrap_or_default()` produced four wrong user-facing claims across three
files and both languages. Finding the first one and fixing only it would have
been the "partial fix leaves sibling paths" shape this repo has been bitten by
before -- so the grep for consumers came before the fix, not after.

**A one-line convenience is where this hides.** `unwrap_or_default()` reads as
tidy defensive code. It is the exact opposite: it is the line that decides an
error means zero, silently, with no comment saying so. The Undo path made the
same decision two hundred lines away and wrote four sentences explaining which
direction it chose and why.
