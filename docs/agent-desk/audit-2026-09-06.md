## Resolved: the ownership half of F1 (`6946832`)

Pass 45 closed F1's path half and recorded the ownership half as open. It was
three defects, not one, all verified against OpenChamber's own source at
`F:\openchamber\packages\web\server\lib\opencode\{mcp,shared}.js` rather than
against documentation:

1. **OpenChamber's row pointed at a file it never reads.**
   `.config/openchamber/config.json` appears nowhere in OpenChamber's source.
   `listMcpConfigs` (`mcp.js:41-55`) calls `readConfigLayers`, which reads
   *OpenCode's* files. A copy to OpenChamber wrote a file nothing would load
   and reported success.

2. **Detection was wrong as a consequence.** `detect_clients`
   (`locations.rs:95-110`) derives presence from the same config paths, so
   OpenChamber was reported "not found on this machine" on machines that have
   it. The chat-import adapter probes the right directory
   (`adapters/openchamber.rs:64-77`); the config side never used it.

3. **OpenCode's own path list was one file of seven.** It reads user paths
   `config.json` -> `opencode.json` -> `opencode.jsonc` and project paths
   `opencode.json` -> `opencode.jsonc` -> `.opencode/opencode.json` ->
   `.opencode/opencode.jsonc`, first existing wins (`shared.js:122-168`).
   GitWyrm declared `opencode.json` and `<repo>/opencode.json` only, so
   anyone whose settings live in `config.json` -- the name OpenCode falls
   back to when none exist -- had their connectors read as absent.

**Settled by two opposing agents** (Q193). The losing option, keeping the row
and adding a `shares_config_with` relationship, correctly identified the
severe failure: two rows over one file makes `client_state`
(`normalize.rs:80-118`, which keys purely on `location.client`) report one
connector as two synced copies, and a `Missing` state is an offer to copy,
which would write the same physical file twice through two receipts.

It lost on a fact it had asserted and the other side disproved: that
`ClientId` also carries chat-import identity. It does not. `AdapterId` is a
separate `&'static str` system, and `adapters/openchamber.rs` contains **zero**
references to `ClientId` or `agent_config` -- checked, not assumed (Q194).
Removing the config row therefore costs the import path nothing, and it
eliminates the double-write hazard outright rather than adding a cross-row
concept to prevent it.

OpenChamber is now named on OpenCode's row via `also_used_by`, surfaced in the
Detected apps list, so someone looking for their app by name still finds it.

**A hazard the path fix introduced, caught before it shipped.** With one
declared path, "write to the first one" was harmless. With three it is not:
writing `config.json` for someone whose settings are in `opencode.json`
creates a file that then *shadows* theirs, because `config.json` is tried
first -- the copy appears to work while every connector they had stops being
read. `choose_destination` now prefers the file that exists, and the test for
it was verified to fail against the old behaviour (Q195).

Retired client keys are kept separately from the live list so receipts written
before this change still name OpenChamber properly (Q196).

## Resolved: the reportable half of F4 (`a9b09c1`)

`plan_limit`/`plan_reset_at` are still hardcoded `None`
(`agent_desk.rs:2622-2623`). Building a real Codex app-server quota adapter
needs a live authenticated provider to verify, which this pass does not have,
and shipping an unverified one would repeat exactly what F3 punished last
pass: asserting a capability nobody checked.

What *was* verifiable is the silence. The panel omitted the row entirely, so
someone asking "how much of my allowance is left" got no answer at all -- not
even "GitWyrm cannot see this". That is the unknown-stays-unknown rule failing
in the direction it was written to prevent (Q197). It now says "not reported",
the vocabulary already used for a figure an agent did not send, and stays
quiet on a chat with no figures yet.

The row was also labelled "Premium interactions", one AI service's own billing
term appearing nowhere else in the product (Q198).

Two design signals came from existing tests rather than from me: the
zero-guard caught the row appearing beside "0 helpers active", and the
zero-window test caught it appearing on a card whose only figure produced no
row. The gate is now keyed off rows actually built, not raw fields.

## New ground: hand-written copies of cross-boundary shapes (`a9e53ce`, `26bd08e`)

Q150 found ten components no pass had ever named. Re-running that search
found **zero** unnamed components now -- the gap has moved entirely into
hooks, `src/lib` pure-logic modules, and the Rust backend.

The sharpest finding there: **four Agent Desk event payloads were described
twice**, once in Rust and once by hand in TypeScript, with nothing comparing
them (Q199). `tauri-specta` only walks types reachable from a
`#[tauri::command]` signature, so an event payload reaches the exporter only
via an explicit `.typ::<T>()` in `lib.rs`. That line existed for
`SelectDeskTarget` and `RunEventKind`; it had never been added for
`OpenSourceTarget`, `OpenResultDiffTarget`, or `SelectSessionTarget`.

The consequence is the dangerous kind: renaming a field in Rust compiles,
typechecks, and passes every test, while "View source", "View diff", and Fix
with AI's landing on its own chat break at runtime. Confirmed by doing it --
before the fix the rename was silent; after, it is a TypeScript error naming
the exact line.

`eventPayloadContract.test.ts` now walks every listener in the chat workspace
and fails if a payload goes back to being declared locally. Writing it found
the third instance (`SelectSessionTarget`) that reading had missed.

**The check was wrong twice before it was right** (Q200), which is the Q142
pattern again: it first reported four correctly-importing listeners as broken,
because inside a multi-line import each name sits on its own line and reads
exactly like a declaration. Both false-positive rounds are recorded in the
test's own comments so the next person does not re-derive them.
