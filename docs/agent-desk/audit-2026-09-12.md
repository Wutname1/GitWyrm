## The locator question: closed as "no", with evidence

Pass 51 shipped the refusal half of the colliding-id defect and recorded the
"real fix" as still open: an additive locator threaded through the adapter
trait so the right file can be found. This pass put that to two agents.

**The answer is no, and the reason is measurable.** The refuse side checked
this machine: **219 real VS Code chat session files** (I re-ran the count
independently), every one a UUIDv4. Two independent conversations colliding is
a 122-bit birthday problem. The only route in is a *copied file* -- restored
backup, synced profile, cloned machine -- and there the two rows are usually
the same conversation twice, where "pick the right one" has no meaningful
answer.

The locator side made a genuinely strong case on cost: `ImportPicker.tsx:176`
already holds the whole summary at the import call site, so threading it is
one line there. That is true, and it is why the question was worth asking.
What it could not overcome is that the cost is not at the call site -- it is
a nullable field on a nine-implementor trait that eight of them ignore
forever, plus regenerated bindings, for a state that needs an unusual setup to
reach at all.

**The refuse side's own correction strengthened its case**, which is worth
recording. Asked to double-check, it found `model.rs:277` bakes
`external_session_id` into `imported:{adapter_id}:{external_session_id}` --
the permanent provenance key, on top of the ledger key already known. So a
wrong import under a colliding id does not merely mis-file one conversation;
it writes a provenance string pointing at the wrong source forever. That is a
stronger argument for refusing than the one it opened with. Verified at
`model.rs:273-278`.

Recorded as **settled**, not deferred. `AmbiguousSession` already carries
`matches: u32`, so the error is the natural place to hang a remedy if a real
user ever reports one.

## Acting on the losing argument: OpenCode skills (`b8971ff`)

The refuse side did not only argue its own case; it named what to do instead
-- **F3, skills copy only to Claude Code** -- on the grounds that every user of
the other adapters hits it on the normal path today, with no unusual setup.
That is a better claim on user impact than the locator, and it was right.

Pass 45 fixed the *wording* of this limit ("GitWyrm cannot copy skills to X
yet" rather than falsely asserting X has no skills). The limit itself was
never lifted, because it needed a verified skills layout for another client.

`F:\openchamber` supplies one. OpenCode's own loader
(`shared.js:12,530-549`) keeps skills at `~/.config/opencode/skills` and
`<repo>/.opencode/skills` -- note the asymmetry, which is OpenCode's, not a
mistake -- and `walkSkillMdFiles` looks for `SKILL.md`, the same
one-folder-per-skill shape `skills::read_skills_at` already reads. So the
reader needed no change at all: the row declares the kind, and the folders are
named.

A new guard walks every client and fails if one declares skills without
saying where they are. That combination would scan nothing and report the
person has none -- indistinguishable from really having none, which is the
"absent looks like empty" failure this project keeps finding. Verified to fail
against exactly that state.

**What this does not claim.** GitWyrm can now find and copy OpenCode skills;
nobody has watched a real skill move between two real installs. The
competitive audit's requirement for F3 was "demonstrate one real cross-client
copy before advertising a Skill/MCP Manager", and that remains outstanding --
it is F10 work, not something a test can stand in for.

larger piece of work came from the side that lost: it argued its position, and
then named what deserved the effort instead. That instruction was better than

question asked.
