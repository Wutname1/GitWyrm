## How this was found

A scan for exported helpers in `components/domain/agent-desk` that no test
imports returned exactly one: `undoCountLine`, in the panel that throws an
agent's work away. One untested function, in the most destructive action in
the workspace.

## Keep disappeared, and the refusal written for it was unreachable (`22fe4df`)

`resultActionAvailability` computed `hasChanges` from
`changedPaths.length > 0`. An unreadable folder has an empty list, so **Keep
was never drawn**.

Pass 65 had already written the other half: `has_landable_changes` answers
*true* for an unreadable worktree, precisely so `keep_result_at` can return
`KeepResultOutcome::WorktreeUnreadable { detail }` -- a refusal naming the
problem and suggesting closing whatever holds the folder. `explainKeepOutcome`
even carries its sentence, with a comment saying it is "deliberately not the
sentence above".

None of it could be reached. The button that would ask for it was hidden by a
copy of the rule that had not been updated. Work in that folder had no path to
being kept, and no explanation.

## The panel contradicted itself (`22fe4df`)

`undoCountLine(record.changedPaths.length)` returns *"The agent made no file
changes, so there is nothing to keep"* for zero -- inside a dialog titled
"Throw away this work?", nine lines below a summary line that pass 65 fixed to
say *"Could not read this folder, so what changed is unknown."*

Same panel, same render, two contradictory claims about one folder.

## What the debate settled, and the fact that decided it

One side argued the frontend should mirror the backend's stance; the other
that a rule living in two languages will drift forever and the backend should
own it outright, shipping a `landable` state across the bindings.

**The second side's own counter-argument decided it, and it was right.**
`keep_result_at` checks `changed_paths_unreadable` **directly**, before it
calls `has_landable_changes`. So the raw field is already the authority, and
TypeScript reading that same field is not a second implementation of a rule --
it is the same one-line rule over the same data. A new binding would have been
ceremony.

Verified by reading the ordering rather than taking either agent's word.

Only `canKeep` changes. `canUndo` already gates on the worktree alone;
everything else gates on state. And the frontend gate is advisory in any case
-- the backend independently enforces every one of these -- so widening it
cannot open a safety hole, only a door to an honest refusal.

## A colocated test that could not exist

The first attempt put the test beside the component, following the convention
`ProviderControl.test.ts` establishes and pass 68's correction that colocated
tests do run.

It failed on `window is not defined`. `ResultReviewPanel`'s import chain
reaches `settingsSync`, which touches `window` at module load, so a test
wanting one sentence brings a browser with it.

So `undoCountLine` moved into `src/lib` beside the rest of the review logic.
That is the same shape earlier passes used -- but for a reason those passes
stated wrongly. It is not that tests only run under `src/lib`; it is that some
components cannot be imported at all outside a DOM. Pass 68 corrected the
claim; this pass found where the real constraint bites.

## Note on method

**Point a finding's own method note back at its own earlier work.** Pass 65
changed a backend rule and its nearest frontend consumer. Two further
consumers of the same fact went unexamined for four passes. The grep that
would have caught it -- who else reads `changedPaths.length`? -- costs nothing
next to the fix.

**A repo's stated constraint and its real constraint can differ, and both
matter.** Two passes ago the config comment was wrong about scope; this pass
found the true limit behind it. Correcting the first was what made the second
findable.
