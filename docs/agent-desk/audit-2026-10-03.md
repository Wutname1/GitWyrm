## VS Code read as not installed on Windows (`82e8639`)

The registry declared VS Code Copilot's settings as
`[".config", "Code", "User", "settings.json"]`, and `personal_locations`
joined those onto the **home** directory on every platform.

That is the Linux path. VS Code keeps settings under the per-user
application-data folder: `%APPDATA%\Code\User` on Windows,
`~/Library/Application Support/Code/User` on macOS.

**Verified on this machine**, not reasoned about:

| path | exists |
|---|---|
| `%APPDATA%\Code\User\settings.json` | yes |
| `%USERPROFILE%\.config\Code\User\settings.json` | no |

`detect_clients` marks a client present only when a declared location
`is_file()`, so on Windows -- the platform GitWyrm ships an installer for --
Copilot read as **not installed**. Its connectors never appeared, and it could
never be a copy destination. That also made every JSONC read/write fix from
passes 70-72 unreachable for the one client they were written for.

**And it is worse than an absence.** `write_supported` stays `true`, and a
destination with no file yet is *created*. So had the path been reachable,
copying a connector would have written a brand-new settings file into a folder
VS Code has never read, and reported success.

Checked the other three rows against the same machine: `~/.codex/config.toml`,
`~/.claude/settings.json`, `~/.claude.json` and `~/.config/opencode/*` all
exist. VS Code is the only client whose root is not home, which is why the
assumption held everywhere else.

## The comment that predicted this

`locations.rs`'s header says the module deliberately did not reuse the
chat-import adapters' detection, because both were being built concurrently,
and that "the two should be unified in a follow-up once both have landed, so
client detection has one implementation instead of two that can drift apart."

Both landed. `adapters/vscode_copilot.rs` resolves the directory correctly on
all three platforms. `agent_config` did not. The predicted drift was the bug.

## Why unification lost, and what replaced it

Both sub-agents converged once one fact was established: **OpenCode's two
sides read different directories on purpose.** Its adapter reads a SQLite
database under `~/.local/share/opencode`; the registry declares configuration
under `~/.config/opencode`. "One root per client" is too coarse to be correct,
so merging the resolvers would have forced a false equivalence.

The two also ask different questions: the adapter asks whether Copilot Chat
has been *used* (it requires an actual session file); `agent_config` asks
where the settings file *is*. Both are right for their caller.

So the root is now declared per registry row (`PathRoot::{Home, AppData}`) --
data, not a third detection implementation -- and a test asserts the two sides
resolve the **same folder** for VS Code, failing the build if they diverge
again. The agreement that matters is checked; the difference that is
legitimate is left alone.

## Note on method

**Check a path against the machine, not against the code.** The decisive
evidence here was two `ls` calls. Every previous pass in this sequence reasoned
about paths from the source; this one asked the filesystem, and the answer was
immediate and unarguable.

**A deferred fix is a finding with a date on it.** The comment did not describe
a past correction -- it described one that had not happened yet, and said what
would go wrong. That is the most checkable kind of comment in a codebase, and
it had been sitting unchecked while three consecutive passes fixed bugs in the
very client it concerned.
