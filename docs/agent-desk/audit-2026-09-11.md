## The last carried import finding: two conversations, one id (`af1deb5`)

`vscode_copilot.rs`'s `read_session` resolved an id by taking the **first**
match from `find_all_session_files`, which is directory-iteration order across
every `workspaceStorage/<hash>/` folder. VS Code keeps one folder per
workspace and does not promise ids are unique between them -- a restored
backup, a synced settings profile, or a cloned machine reproduces one.

The listing correctly showed both as two rows in two different projects.
Clicking either opened the same conversation with the other's project name
beside it. Reverting the fix shows why nothing downstream could catch it: the
call returns `Ok(...)` with a real title, a real project path, and three real
messages. It is indistinguishable from a correct answer.

### The decision, and the fact that settled it

Two agents argued qualifying the id (`<workspace_hash>/<id>`) against refusing
the ambiguous read. They disagreed on the crux -- whether changing the id's
form would orphan the import ledger -- so I checked rather than picking a
winner.

**The refuse side was right, and it is not close.**
`import_store::already_imported_session` is a bare
`ledger.sessions.get(external_session_id)` -- an exact-key lookup with no
normalisation, no fallback (`import_store.rs:163-167`). The only production
caller passes the id verbatim (`agent_import.rs:411`). So a new id format
misses **every** existing entry, and `import_store.rs:148-157` states what
happens next in its own words: the create path "builds a session with a fresh
id, never reading the one already on disk -- so a lost write there does
duplicate the whole chat."

That is the user's entire import history re-imported as unlinked duplicates,
to fix a bug that needs a cloned machine to occur. The qualify side proposed a
compatibility fallback, but it lived in `read_session`, not the ledger lookup,
so it would not have saved the key -- which is exactly the kind of thing that
only surfaces by reading the call site.

**Both agents were useful.** The qualify side independently verified something
that mattered: `external_session_id` is never rendered anywhere in the UI --
only a React key and an opaque argument. That killed the "a qualified id is
unreadable to humans" objection outright, and it is worth having settled even
though its own proposal lost.

### What shipped, and what it does not claim

`AdapterError::AmbiguousSession` and `ImportSessionOutcome::AmbiguousSession`,
with plain-language copy on both paths. The two exhaustive `switch`es in
`agentImportDisplay.ts` failed to compile until the copy existed, which is the
error-handling design working as intended.

Deliberately kept separate from `CorruptSession`: nothing is damaged, and
telling someone their file could not be read sends them hunting for a fault
that is not there. A test pins that the wording never says "corrupt",
"damaged" or "could not be read", and another pins Rule #2 against a jargon
list.

**This does not fix the underlying problem and does not pretend to.** Those
two conversations become unimportable rather than wrongly importable. The
honest disambiguation -- an additive `workspace_hash` field on the summary,
used for resolution while `external_session_id` stays byte-identical -- is
recorded below as the real fix, in the shape the losing agent itself
recommended for whenever it is taken.

`claude_code.rs`'s `find_session_file` has the same first-match shape at a much
lower risk (its ids are UUIDs). Left alone this pass: same reasoning, and no
demonstrated collision.

## Note on method

The fix was verified by reverting it and watching the test fail. That output is
the clearest artefact this pass produced: it prints the whole wrong
conversation, titled and populated, as an `Ok` result. A defect that returns
plausible data is the kind no amount of reading finds.

**When two arguments disagree on a fact, the fact is the work.** Three passes
of debates have now produced one convergence, one where the losing side
supplied the decisive evidence, and this one -- where both sides were
confident and only reading the call site settled it. The debate is worth
running for the evidence it surfaces, not for the verdict it offers.
