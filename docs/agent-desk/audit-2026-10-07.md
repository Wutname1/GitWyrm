## A failed read reported as an empty record (`13e3677`)

`read_results` is careful, and its comment says so: a missing results file is
the ordinary "nothing to review" state and returns an empty list, while
"every other error (malformed, unsupported version, unreadable) still
propagates so a genuinely damaged file is reported rather than silently
treated as empty."

`enforce_completion_condition` then called it with **`unwrap_or_default()`**,
which flattens exactly the distinction the function was written to preserve.

And an empty list is not neutral here. It is the precise input `judge` reads
as *this helper changed nothing*:

> It was asked to change specific files, but it left no changes at all.

The helper is then marked `Failed` and the code returns before integration.
So a damaged sidecar destroyed the work of a helper that may have changed
every file it was asked to -- and told the person, in the chat, that it had
changed none.

The fix separates the two at the call site, where the difference still
exists. Still refused -- nothing should be merged when GitWyrm cannot tell --
but the sentence now names GitWyrm's own failure. That is the same answer
`judge` already gives one branch below for an unreadable worktree, which was
the model.

Verified by restoring `unwrap_or_default()` and watching the new test fail,
printing the old sentence verbatim.

## Two refusals, now one implementation

The refusal path (mark `Failed`, record the reason, write the chat note) was
inline. Adding a second caller would have meant a second copy, and a second
copy of "how we tell someone their work was dropped" is how two paths drift
into describing one outcome differently. Extracted to `refuse_completion`
before adding the caller, not after.

## The other two call sites, checked and left alone

`read_results` has three `unwrap_or_default()` callers. Only one was wrong,
and the difference is what the empty list goes on to drive:

| site | effect of a damaged file | verdict |
|---|---|---|
| `agent_graph.rs` completion judge | helper marked Failed, work dropped, false sentence | **fixed** |
| `agent_result.rs` orphan scan | reports "no orphans", hiding worktrees on disk | misleading, not destructive -- left |
| `agent_result.rs` all-sessions sweep | one damaged session would abort the whole sweep | correct as-is |

The last is the interesting one: there `unwrap_or_default()` is the right
call, because the loop's job is to survey every session and one bad file must
not blind it to the rest. The same idiom is right in one place and wrong in
another, which is why grepping for it proves nothing on its own.

## Note on method

**When a defect is found in one arm of a match, read the other arms.** Pass
75 examined `ChecksPass` closely and did not look at `FilesChanged`, four
lines below, which had the same defect arriving from upstream instead of from
a missing producer. The shape was already named; only the route differed.

**A function that carefully returns `Result` is making a claim its callers
can break.** The comment inside `read_results` is exactly right and was
already there. The defect was one word at a call site, undoing it.
