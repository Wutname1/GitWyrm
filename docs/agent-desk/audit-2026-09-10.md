## Fixed: a message count that was arithmetic, not a count (`1ee131c`)

The VS Code listing answered `requests.len() * 2`. A turn actually produces
one message always (the person's, or a placeholder), plus one for the reply
when it has text, plus one for tagged parts when there are any -- one to
three, never reliably two. So the picker promised a number and opening the
conversation showed a different one, in both directions.

**A near-miss worth recording.** My first fix wrote a separate counter that
walked the same parts. Checking it against the read path rather than assuming
it matched found a case where they disagreed: two plain parts both carrying
empty values make the read path emit a bare newline, which is *not* empty, so
it produces a message my counter would have missed. Replicating a quirk in a
second place is how the original defect happened. Both paths now call one
`reply_of`, so they cannot diverge at all.

## Fixed: one unreadable byte discarded a whole conversation (`7c45370`)

`read_foreign_file_to_string` used strict `read_to_string`, which fails the
entire file for a single invalid byte. The listing path reads the same file
line by line and skips the bad line -- so a conversation listed with a title
and a message count, then refused to open, losing every message including the
ones the list had just shown.

Ordinary triggers: a half-written multi-byte character at the end of a file
the other tool is still appending to, or a pasted fragment in another
encoding. Now read as bytes and converted lossily, so every readable message
survives. One shared function, so all four adapters are covered.

## Settled, and deliberately not refactored: the 1970 sentinel (`024512f`)

When an external conversation records no date, all four adapters substitute
`"1970-01-01T00:00:00Z"` -- 17 sites. `ExternalSessionSummary.updated_at`'s
own doc says it is "taken from the file/record itself, never from import
time", and that value is neither.

Two agents argued making it `Option` versus leaving the type alone. **They
converged**, which is the useful outcome: both independently found that the
import picker renders no date at all, so the "Jan 1, 1970 in the picker" harm
does not exist; and both identified `agent_import.rs:663,777` as the one place
the sentinel escapes onto `AgentSessionHeader.updated_at`, which the sidebar
*does* render. The pro-refactor side conceded its own weakness plainly:
"17 substitution sites... done halfway, this is pure type churn buying
nothing."

The visible harm, verified: `formatCompactAge` parses the epoch successfully
and renders **"56y"** -- a confident, absurd measurement of something GitWyrm
was never told. It already returns `'--'` for an unparseable date, so the
honest-absence pattern exists; the sentinel simply parses.

Guarded at that one boundary. When the original recorded no date, the header
takes the import time -- a date GitWyrm genuinely measured. The type change is
recorded as still-open below rather than done halfway.

## Note on method

Every fix was verified by reverting it and watching the new test fail. The
message-count test is the clearest example: reverted, it fails with "session
session-fixture-0001 was listed with 2 messages and opened with 3" -- the
defect stated as the user would meet it.

Two observations after three passes of commissioned audits:

**Converging arguments are the strongest signal.** The 1970 debate produced
agreement on both the facts and the conclusion, including the pro-change side
naming its own weakness. That is worth more than a winner, and it turned a
17-site refactor into a three-line guard.

**Verify the fix against the thing it replaces, not against the description
of it.** The message-count near-miss was caught only by comparing my counter
to the read path line by line. A fix that reimplements behaviour is a second
place for the same bug to live.
