## The warning that pointed the wrong way (`8b021e9`)

A run's output reaches the window twice. `ai-run-event` drives the live view.
Separately `route_run_event` writes the message to the session file and only
then emits `agent-session-event` -- persist-before-emit, a documented rule.

Events are numbered per run, and a skipped number is how the window notices a
message never arrived. `ConversationPane.tsx` then draws:

> Some of this chat did not reach this window. Close it and open it again to
> load the full record.

That sentence is correct for the case it was written for: the file has the
message, the window missed it, reopening loads it. `agentSessionStore.ts`
spells the premise out -- "A sequence gap is a DELIVERY gap ... Nothing was
lost from the record" -- and reasons carefully from it to the conclusion that
clearing the warning on refetch is right.

**The premise is false for the one path where the file is what is missing the
message.** `RunEventRouted::WriteFailed` logged a warning and returned. Its
comment said "the run itself is unaffected, only its durable copy is missing",
which is true and is exactly the problem: the number had already been spent
(`airun.rs` takes it before routing), no `agent-session-event` was emitted for
it, and the next successful event read as a skip. So a failed *save* produced
the warning for a failed *delivery*, whose advice sends the person to the
emptier copy and away from the only one that has the message.

**A second way to see it on a healthy chat.** `NoLinkedSession` and
`Ignored` -- no session linked to this repository, or a duplicate -- record
nothing by design, but were spending a number anyway. The next real event then
looked like it had skipped one. A completely whole chat drew the warning.

Both halves fixed:

- `release_sequence` hands back a number taken for an event that was never
  recorded, so no false gap is manufactured. Guarded to the most recent number
  only -- putting back a stale one would hand the same number to two events,
  and a repeat is dropped as a duplicate.
- `AgentSessionEventKind::NotSaved` carries no message content, only the fact
  that a write failed, so the window can tell the two situations apart. The
  number is deliberately **not** released there: that gap is telling the truth.

The banner now branches, and shows the unsaved message alone when both are
true -- it is the one with something to lose, and its advice contradicts the
other's.

## What the debate settled, and what I had to check myself

Two sub-agents argued messaging-layer versus write-path. Both were partly
right and both conceded the other's half in their own counter-argument, which
is the outcome the exercise is for.

**One shared premise was wrong, and neither caught it.** Both argued that
reopening the chat *destroys* the unsaved message via `clearSession`. It does
not: `clearSession` runs only when `liveOverlayIsRedundant` says every live
message is already in the durable record, and an unsaved message keeps that
false. So the overlay survives, and the message with it. The advice was
useless, not destructive -- a real defect, a smaller one than argued. An app
restart does lose it, with nothing on disk recording that anything went
missing.

Correcting that mattered: had I accepted it, the fix would have grown a
sentinel file and a retry loop on the hot path of every run event, under a
session lock -- the shape this repo's own notes blame for freezing the app.

**A rule quoted from memory turned out to be nine words.** "Persist an event
before emitting it to the UI" is one line of design.md, written about message
events. A notice that carries no message and describes the store's own failure
is outside its subject matter -- but nine words cannot settle that, and
whoever owns design.md should add a sentence rather than let `airun.rs` hold a
quiet exception.

## An edge the old path could not reach at all

If the **first** event of an execution fails to save, there is no previous
number to skip from (`lastSeen === 0` is not a gap), so no warning was ever
possible. The `notSaved` notice fires regardless of position, so that case is
now covered where before it was silent.

## Note on method

**Two tests, two different jobs.** `a_number_taken_for_nothing_goes_back`
fails with the fix removed. `releasing_a_stale_number_changes_nothing` passes
with the fix removed -- it does not pin this defect, it pins the plausible
wrong version of the fix (decrement unconditionally), and it was verified
against that version rather than assumed. Worth keeping and worth labelling as
what it is; a test that cannot fail for the defect it sits beside has to earn
its place some other way.

**Competing arguments are evidence, not verdicts.** Both agents cited real
file:line and both built on a premise about `clearSession` that fifteen
seconds of reading disproved. The debate was still worth running -- it
produced the two-halves answer -- but the checking was mine to do.
