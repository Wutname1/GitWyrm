Recorded against `agent-desk-openchamber-audit-0f40fb` at `a18a860` (merged with `main`).
This is a fresh read of the code against the Agent Desk vision, not a re-reading of the
previous audits. Where an earlier document and the code disagree, the code wins and the
disagreement is recorded.

- `npm run typecheck`: passed.
- `npm run test:unit`: 73 files, 906 tests passed.
- `cargo test --lib`: 1,516 passed, 0 failed, 10 ignored (the ignored ones are real-binary provider runs).

## Method

Every claim below was checked against the shipped source, not against the specs or the
prior audit notes. Three of the findings I set out to record turned out to be already
closed; they are kept here as *corrections*, because two separate documents in `docs/`
still describe them as open and would mislead the next reader.

## Corrections: documented gaps that are actually closed

These are the highest-value output of this pass. Stale "open" notes cost the next agent
real time, and two of these already cost a previous one.

1. **Graph nodes have no job title or agent name (`gaps-and-contradictions.md` G10/G11,
   "load-bearing fact 2").** Closed. `ExecutionRecord` now carries `job_title`,
   `job_description`, `helper_role`, `allowed_paths` and `completion`
   (`src-tauri/src/agentdesk/model.rs:564-588`), and they are populated from the accepted
   proposal at `src-tauri/src/commands/agent_graph.rs:1030`. The "renders Helper plus a
   hex id" symptom is gone; `agent_graph.rs:1185` only falls back to `"Helper"` when a
   proposal genuinely supplied no title.

2. **The plan checklist rests on a convention nothing produces
   (`gaps-and-contradictions.md`, final section).** Closed. `plan_mode_instruction`
   (`src-tauri/src/agentdesk/plan_proposal.rs:63`) now asks for exactly the
   `- [ ] step` shape `src/lib/agentDeskPlan.ts` parses, and
   `plan_mode_asks_for_the_checklist_shape_the_pane_renders`
   (`plan_proposal.rs:439`) pins the marker so the prompt and the parser cannot drift
   apart silently.

3. **Read-only is advisory / an agent could reach an external service.** Closed, and
   stronger than the prior audit claimed. `check_tool_capability`
   (`policy.rs:556`) is a single enforcement point with `Push` and `PostToHost` as
   first-class capabilities, and `from_acp_kind` fails **closed**: an unknown or absent
   ACP `kind` classifies as `EditFile`, not `Read`. I initially flagged
   `Some("fetch") => Read` as a hole through which a read-only session could POST to a
   host; it is not, because `ALWAYS_DENIED_TOOLS` (`cli_agent.rs:50`) denies `url` at CLI
   launch for **every** run, write or not, and a `--deny-tool` outranks every provider
   allow rule. The classifier is defence in depth behind a bound the CLI cannot be talked
   out of.

## Open findings

### F1 (P2, code) - integration resumability is reasoned, not proven

`agent-desk-agent-graphs` tasks 5.5 and 5.10 are honest that the exactly-once story rests
on code inspection. Confirmed still true: grepping the whole Rust tree for a
restart/exactly-once integration test (`fn .*restart.*integrat`, `exactly_once`) returns
nothing. Per-file writes are atomic (temp-write-then-rename in `write_content_atomic`) and
`integrate_helper_into` skips already-applied operations by comparing text, so the design
is sound. What is missing is a test that kills a batch mid-way, restarts, and asserts each
operation applied exactly once.

Cost of leaving it: a partial integration reported as Finished is precisely the failure the
vision's "nothing lands automatically" promise exists to prevent, and it is the one class of
bug unit tests currently cannot see.

### F2 (P2, code) - symlink integration has code but no test

`create_symlink` / `read_symlink_target` (`agent_graph.rs:1686,1927`) exist and are
platform-split, but no test exercises a symlink through integration. Task 5.10 already
names this. On Windows this path is the most likely to behave differently from the
developer's assumption, since symlink creation can require privilege.

### F3 (P1, process) - the gate is native acceptance, and it is not moving

The largest category of open tasks across every shipped change is not missing code. It is
items only a person walking the built app can close: display scaling at 100/125/150/200%,
keyboard-only traversal, screen-reader names, 1,000-row session lists, Split View across
repositories, two simultaneous same-repo sessions, and a real multi-helper Auto graph.
`release-readiness.md` states this plainly and correctly.

This is the honest bottleneck. More unit tests do not move it, and neither does more
feature work. Recording it here so that a future pass does not mistake "all suites green"
for "ready".

## What I am not calling a finding

- **Usage honesty.** `SessionUsageCard` renders no row for an absent field, marks estimates
  `est.` with an accessible label, and says "not reported" rather than `0`
  (`SessionUsageCard.tsx:73-101`, `agentDeskUsage.ts`). This matches the vision's "unknown
  stays unknown rather than appearing as zero" exactly.
- **Quota (`plan_limit` / `plan_reset_at`).** Unsourced by deliberate decision, not
  omission; ACP exposes no quota. Recorded in `release-readiness.md`. Leaving it blank is
  the honest behaviour, and matching a competitor here would mean per-provider credential
  scraping.

## Rejected

**"The active pane is marked only by a 10% opacity difference."** False positive. The
reviewer read `ConversationPane` in isolation and missed the parent: `AgentDeskView.tsx:222`
draws a 2px Deep Mint inset edge on the active pane and sets `aria-current` plus a
distinct accessible label. That satisfies DESIGN.md's Selected Must Read Rule.

## Deferred, with the reasoning recorded

**The micro floor.** DESIGN.md states nothing renders below 0.6875rem (11px); the app
breaks that ~138 times. Two sub-agents argued the two positions and converged:

- Enforcing found the decisive fact -- 17 files in this directory use `text-2xs` AND
  sub-floor sizes together, and `SessionUsageCard` uses three different micro sizes for
  peer metadata in one card. That is drift, not preference.
- Amending found the decisive counter-fact -- `useUiScale.ts:26` sets
  `document.body.style.zoom`, which scales every `px` value, so a 9px label at 200%
  renders at 18px. The accessibility case is genuinely weaker here than on the web, and
  `AgentGraphPanel`'s node geometry is tuned around the smaller size.

Both agreed on the risk-free subset, which is done. The remaining 49 sub-floor uses are
a judgment call that should be made while looking at the running app, not in a diff --
which puts it in the same place as everything else below.

# Second audit pass, same date

A fresh read against the vision's safety promises, covering ground the first pass did
not reach.

## F4 (P0, fixed in this pass) - "never silently pushes, posts or merges" had no enforcement

The vision's strongest safety promise is that the agent never silently pushes, posts a
review, merges a pull request, or changes an external service. Nothing enforced it.

The capability table has `Push` and `PostToHost` as distinct capabilities, but:

- `from_acp_kind` (`policy.rs:511`) can never return either one. Every provider tool call
  classifies as `Read` or `EditFile`.
- No call site outside `policy.rs` ever constructs them; grepping the whole Rust tree
  returns nothing. The module's own test says so explicitly and honestly
  (`fix_write_gate_does_not_by_itself_authorize_push_or_host_posts_at_kickoff`), noting
  the refusal "is enforced by the caller (kickoff never calls them), not by this table."
- Nothing inspects shell command content anywhere in the tree.

So on an Auto or Fix run - where shell is deliberately allowed, because tests and builds
are how an agent checks its own edits - `git push`, `gh pr merge` and `sed -i` all arrive
at the approval gate as the same kind of thing. And every real gate was built as
`GateRequest::Unclassified` (`cli_run.rs:752`), whose card reads "Allow this: <the
provider's own summary>?".

The person was being asked to approve publishing their work to a server, in a card that
did not say so.

**Fixed.** `GateRequest::Publish { effect }` names the consequence, and
`GateRequest::classify` reads the provider's summary for `git push`, `gh`/`glab` merge,
comment, review and create actions, and plain-language "push/publish to" phrasings. The
card now says what leaves the machine and that undo cannot take it back.

**Deliberately conservative in one direction only.** An unmatched command still gates as
`Unclassified` and still shows its own summary, so a missed publish is a vaguer card
rather than a silent one. `ordinary_work_is_not_mislabelled_as_publishing` pins the other
half: matching is on whole words, so `Edit src/pusher.rs` and `Write to
gh-pages/index.html` are not dressed up as publishing. Crying wolf on ordinary edits
would teach people to click through the one card that matters.

Six Rust tests and one frontend test cover it. Note the type system found three more
renderers of this enum that a grep would have missed (`GateCard.tsx` title and body,
`RunStream.tsx` history) - all three now name the publish case.

## Confirmed holding

- **Read-only intents provably cannot write.** `Ask`, `Explain`, `Summarize` and `Review`
  all carry `can_write: false` and `WorktreePolicy::Never` (`policy.rs:95-124`), and
  `denied_tools_for` adds `shell` and `write` to the launch-time `--deny-tool` set for
  them. That is a bound the CLI cannot be talked out of, not an advisory check.
- **No "don't ask again".** `GateAnswer` has exactly three variants and the doc comment
  states the reasoning: "a remembered approval is a decision made once and applied to
  situations the user never saw." This is the right call and worth not regressing.

# Second design critique: source kickoff and Agent Setup

Surfaces the first critique did not cover. **27/40** on Nielsen's ten heuristics, and the
shape of that score is the finding: language and status score high (4 and 3), while
*control, error prevention and consistency* -- the Operate-mode virtues -- score 2. This
is a surface whose engineering is well ahead of its interface.

## Vision promises, verified one at a time

| Promise | Verdict |
| --- | --- |
| Preview the exact change | Holds. Field-level, server-side, and the batch path reuses the identical card rather than offering a lighter-weight path that skips scrutiny. |
| Back up the destination | Holds in code (`plan.rs:183-186`), and now says so on the glass. |
| Apply atomically | Holds per file (temp, flush, rename, hash-gated). NOT atomic across a batch: a mid-batch failure leaves some apps updated and others not. Per-plan results are shown, so this is honest -- but the promise is true per destination, not per batch. Recorded, not fixed. |
| Real Undo with a receipt | Was half-true. Fixed below. |
| Secrets genuinely redacted | Holds, and well: `redact.rs` matches on field identity rather than guessing whether a value looks token-shaped, so redaction survives a credential that does not look like one. The *visibility* was counterproductive. Fixed below. |
| Kickoff gives an immediate visible response | Holds from panel buttons. Does NOT hold from context menus. Recorded below. |

## F5 (P0, fixed) - a writable destination was written to without ever being offered

`CLIENT_LABEL` names five clients; `CLIENT_COLUMN_ORDER` hand-listed four. The missing
one, `open-chamber`, has a real writer in the backend registry
(`registry.rs:211-224`). The consequence chain:

- `eligibleDestinationsFor` reads the row's own per-client states, not the column list, so
  OpenChamber was **pre-ticked** as a destination.
- The checkbox list renders through `CLIENT_COLUMN_ORDER`, so it had **no checkbox** and
  could not be unticked.
- The table builds columns from the same constant, so its sync state was **invisible**.

A copy could therefore be written to it without ever appearing as a choice -- the same
"wrote to an app nobody selected" failure `BatchReviewDialog` was built to prevent,
reintroduced one constant away.

**Fixed** by deriving the order from `CLIENT_LABEL` so a client appears the moment it has
a name, plus the invariant test that did not exist: every named client has a column,
exactly once, and `open-chamber` specifically is present.

## F6 (P1, fixed) - Undo reported success whether or not it succeeded

The undo mutation resolved `UndoOutcome` and discarded it. The backend distinguishes five
outcomes, and the one that matters most is `concurrentChangeRefused`: the destination
changed after the copy, so undoing would clobber a newer edit and **nothing was touched**.
The person pressed Undo on another application's config, saw no error, and believed the
file was restored when it may not have been.

**Fixed** with `explainConfigUndoOutcome`, following the `explainUndoOutcome` pattern this
codebase already uses for an agent run's own undo. Restored reports success; every other
outcome reports plainly what did not happen.

## F7 (P2, fixed) - the best safety guarantee was invisible, and its one visible moment was inverted

`plan.rs` reads and hashes the destination, refuses on mismatch, writes a byte-identical
backup, writes a receipt, then temp-writes and atomically renames. The dialog said
"Apply". The user's blocking question before overwriting another application's config is
"what happens to the file that is already there?", and the answer was excellent and
unsaid.

Worse, the one moment the product actively protects the person -- leaving an API key
behind -- was rendered in warning amber with an alert shield, below the type floor. That
reads as "my token broke", not "GitWyrm protected me".

**Fixed:** the redaction notice is now green with a check shield at the type floor, and the
apply footer states the guarantee in the user's terms: your current file is saved first,
and if it changed since the preview nothing is written. Both claims verified against
`plan.rs` before the copy was written.

## Recorded, not fixed

- ~~**Context-menu kickoff shows nothing.**~~ **Fixed.** The busy state was set
  synchronously and correctly, but a Radix menu unmounts on select, so it rendered into a
  component that no longer existed: the right-click gesture the vision leads with had the
  weakest feedback on the surface. An immediate loading toast outlives the menu, and all
  six outcome paths replace or dismiss it by id rather than stacking a second toast.
- ~~**Batch apply is not atomic across plans.**~~ **Disclosed.** Verified against
  `agent_config_apply_batch`, which maps plan-by-plan with no rollback across them. The
  dialog now says so before the decision rather than only in the results afterwards.
- **Sub-floor type is systemic, not local.** 108 arbitrary sizes repo-wide. Same deferred
  decision recorded in the first critique; the reasoning has not changed.

# Third audit pass, same date

Covering OpenSpec integration, recovery, and the graph node contract.

## Confirmed holding (no finding)

- **OpenSpec exact-task acceptance is real and wired.** `complete_openspec_task_at`
  (`agent_desk.rs:3196`) re-parses `tasks.md` fresh rather than trusting a cached line
  number, locates the task by `locate_target_task` (index AND text, so a task that moved
  is still found), and writes through `write::toggle_task_line` -- the same function the
  Spec Desk checkbox calls. It is registered, invoked from the result panel, and returns
  typed outcomes for every failure. The older docs describing "the completion hook has no
  consumer" are stale.
- **Recovery reconciliation is sound and precise.** Every session read reconciles each
  execution individually against the in-process `ExecutionRegistry`, so a restart marks
  exactly the lost processes `Interrupted` -- per execution, not per repository. The list
  path reconciles for display without persisting, and the reasoning for that split is
  written down: persisting per row would mean a lock plus a read-modify-write on every
  sidebar refresh, and the durable fix happens when the session is actually opened.
- **Usage honesty holds at the per-agent level too.** `buildAgentUsageLines`
  (`agentDeskUsage.ts:166`) contributes no part for an absent figure, so an unreported
  number is blank rather than zero.

## F8 (P2, fixed) - a chat never said how old its saved copy was

Every non-manual `SessionSource` carries a `SourceSnapshot` with `captured_at` and
`live_unavailable`. The flag was surfaced in two places; **the timestamp was never
rendered anywhere in the app**.

The snapshot exists so a chat still reads correctly after the issue, PR or spec moves on.
That only works if the person can tell they are looking at a saved copy. Without it a
summary captured months ago looked exactly like a live one, and "No longer available"
announced that the source was gone without saying that the panel was still showing the
saved copy of it.

**Fixed** with `describeSnapshotFreshness`: "Checked 3 hours ago" normally, and "Saved copy
from 3 hours ago. This is what the chat still shows." when the live source cannot be
reached. Six tests, including that an unreadable timestamp produces no line rather than a
guess. The compact banner carries the same sentence as a tooltip rather than a second row.

## F9 (P2, fixed) - a blocked helper looked identical to a stalled one

The vision specifies a graph node showing "its assignment, provider and model, allowed
files, dependencies, activity, usage, output, and result." `depends_on` has been on
`ExecutionRecord` since graphs shipped and was **never rendered anywhere in the
frontend** (zero matches for `dependsOn` outside the generated bindings).

So a helper sitting idle because a peer had not finished yet was visually identical to one
that had stalled. The person could not tell "blocked" from "broken", which is exactly the
distinction that decides whether to wait or to intervene.

**Fixed:** the inspector now shows "Waiting for <name> to finish first", resolving ids to
job titles from the session's own executions and falling back to "another agent" rather
than leaking a hex id.

## Recorded, not fixed

- **Per-node usage is still not shown.** `ExecutionRecord.usage` exists and the session
  card already breaks usage down per agent, so the graph inspector is the one place a
  node's own cost is absent. Lower value than the dependency line -- the figure is
  reachable in the Usage panel -- so it is recorded rather than done.

# Third design critique: OpenSpec, recovery, and the Spec Desk handoff

**23/40.** The lowest score of the three critiques, and the shape says why: the writing
layer scores 4/4 (match with the real world) while error prevention scores 1/4. The happy
path here has been built and polished; the unhappy path has been carefully *specified* --
the outcome enums are meticulous -- and then not surfaced.

The critique's own summary of the pattern is the useful part: **three backend capabilities
that constitute the stated differentiator are built, typed, tested, and unreachable from
the UI.** Every fix below is putting a computed value on screen rather than writing new
logic.

| "Tell the spec" was ungated | Every other landing action gates on result state; this one gated only on source kind and AI config, so it was live while a result was still under review, after a revision was requested, and after Undo -- discarded work could be written into the project's source of truth | `canTellSpec` joins `resultActionAvailability`, true only after Keep or Commit, with tests for both halves |

## A test that was wrong, not the code

Two existing tests failed against these fixes, and both turned out to be asserting a
*mechanism* rather than their own stated intent:

- `does not get the working or waiting dot tone` asserted `undefined`. But `undefined` is
  the neutral dot, which is exactly how an interrupted agent came to look calmer than a
  live one. The test now asserts what its name says -- not working, not waiting -- and
  that the node is not silent either.
- `is excluded from the working/waiting counts` asserted the exact string `2 agents`.
  Keeping that literal would have meant leaving a dead agent out of the header a person
  glances at. It now asserts the exclusion it names, plus that the stopped agent is
  visible and the total survives.

Worth recording because the second one caught a real regression in my own first attempt:
counting stopped agents initially made a finished graph read "1 stopped" and drop the
total.

## Recorded, not fixed

- **"Tell the spec" still bypasses the diff review Spec Desk requires for the same
  operation.** Spec Desk routes AI edits through `DraftedEditReview` (a real diff with
  +/- counts and Accept/Reject) before touching a draft; Agent Desk calls `replaceDraft`
  directly. Both write to the same files. The unsaved-tab marker closes the *visibility*
  half of this, so the draft can no longer sit unnoticed -- but the review gate itself is
  a larger change: `drafted` is `DeskDetail`-local state that Agent Desk cannot reach, so
  closing it properly means lifting that into a store. Worth doing, too big to do safely
  at the end of a pass.
- **No way to restart a single failed helper.** The inspector now says a node failed and
  in what tone, but the only recovery is still Stop all and re-plan.
- **Per-node usage** remains unrendered (recorded in the third audit pass above).

# Fourth pass, 2026-09-04: the everyday conversation surfaces

**29/40** on the transcript, composer, sidebar and Split View. The shape of the score is
again the finding: 4s in language, minimalism and error recovery; a **1 in user control**
and 2s in recall and efficiency. The critique's own summary of the cause is exact -- this
is a surface built by someone who thinks hard about wording and honesty, and has not yet
lived with two hundred sessions or a runaway run.

## F10 (P0, fixed) - a running solo agent could not be stopped

`agentSessionStopExecution` had exactly two callers, both inside `AgentGraphPanel`. That
panel is only offered when `sessionHasGraph()` is true, which requires a helper or a
proposed graph -- so it is **never** shown for a solo chat. Solo is one of the two team
shapes and the more common one.

`SessionComposer`'s own doc comment recorded the decision: "There is deliberately no
separate stop/icon-only button beside it; 'Stop all' lives only in the Graph panel
header." That reasoning is sound for a team run and silently fails for a solo one. The
result was that an agent in Auto mode, editing files in the person's repository, could not
be stopped from anywhere in the app -- closing the window was the only way out, and it
produces the honest but bleak "This chat stopped when the app closed."

**Fixed:** Send becomes Stop while the chat is working, preparing, or waiting on input,
reusing the Graph panel's exact outcome handling so the two controls cannot report the
same event differently.

## F11 (P1, fixed) - the row hid the project, in the grouping mode that is the default

`SessionRow` rendered provider glyph, title, and age. The project appeared only as a group
header under Project grouping -- and Recent is the default. So a row reading "Fix the login
redirect" gave no clue which of several open repositories it belonged to.

This is DESIGN.md's own Persistent Context Rule ("Repository ... stay visible whenever they
help prevent work in the wrong place"), broken on the surface that rule most protects.

**Fixed:** the project name follows the title, muted and truncating first so it can never
squeeze out the name, and is suppressed under Project grouping where the header already
says it. A test pins that the flag is set for exactly that mode.

## F12 (P1, fixed) - three selected states were a faint tint alone

DESIGN.md: "A selected control needs persistent contrast, an edge, a check, or another
unmistakable marker. A faint tint alone is not a selected state." Three surfaces used tint
only, while `NewChatLanding`, `ProviderControl` and `TeamShapeControl` all did it correctly
with a `border-primary` edge -- so the system knew the answer and three places had not
applied it.

The worst was the operating-mode pill: `bg-soft text-accent-text` with no edge, on the
control that decides whether an agent may change files. Also the grouping tabs (a one-step
tonal shift) and the selected chat row.

**Fixed:** a mint edge on all three, matching the treatments already in the system.

## F13 (P1, fixed earlier this pass) - no way to find one chat

Found independently by this critique and by the audit: `titleContains` is implemented and
tested in the backend filter, threaded through the frontend hook, and passed `null` from
every call site. Fixed before the critique landed; recorded here because two independent
reads reached the same place.

## Recorded, not fixed

- **The thought block is dead code with a loaded promise.** `MessageKind::ThoughtSummary`
  is never produced by any live path -- `bridge.rs::message_kind_for_step` maps every
  `RunStep` to something else, and it is set only in a unit test. So `ThoughtBlock` never
  renders today. But its lead word ("Thinking"/"Reviewing") is chosen by the renderer, not
  supplied by the provider, so the moment anyone maps a raw streamed note to it, GitWyrm
  starts asserting a model was thinking. The right fix before it is ever wired up is for
  the label to come from the message and carry provider attribution. Worth doing when that
  path is built, not before.

# Sixth pass, 2026-09-04: Undo refused on every result

## F20 (P0, fixed) - the safety net the whole review design leans on was unreachable

The most consequential bug found in six passes, and it was hiding behind a green suite.

`undo_result_at` asked `worktree::dirty_count()` "is anything uncommitted in this
worktree?" and, if so, returned `RefusedHandEdited` -- telling the person their work had
"N hand-edited changes since the agent finished."

But **an agent's output is uncommitted by design**. `changed_paths_for_worktree` builds the
result's own file list from `repo.statuses()`; `dirty_count` reads the same `repo.statuses()`
walk. `keep_result_at` only flips state to `Kept` and writes the sidecar -- it touches no
git object. So the two functions asked the same question and one of them called the answer
a hand edit.

**Proven, not argued.** A test written before any fix
(`undo_works_on_an_ordinary_result_nobody_touched`) built a worktree holding exactly what an
agent that creates one file leaves behind, asserted the result recorded that one change,
pressed Undo, and got `RefusedHandEdited { modified: 0, untracked: 1 }` -- the agent's own
file, reported to the user as their edit.

### Why the suite did not catch it

`worktree_with_a_change()` -- one commit plus an uncommitted `b.txt` -- was used by **nine**
tests as "the worktree the agent worked in" and by `undo_refuses_a_hand_edited_worktree` as
"a worktree a human edited." The same fixture proved both claims, because at the filesystem
level there is no difference between them. And `undo_discards_a_clean_worktree` passed only
because its worktree was clean, which for a real run means the agent changed nothing.

Two tests asserting opposite outcomes on byte-identical input is not a subtlety; it is the
defect written down twice.

### The fix, and the one deliberately not taken

Two sub-agents argued the options against the vision.

**Taken: compare against what this result recorded.** `count_unexpected_paths` compares the
live worktree against `record.changed_paths` as a `BTreeSet` of (path, status), so ordering
-- which git2 does not promise -- can never read as a change. Refusal now counts only paths
the agent did not leave.

**Not taken: commit the agent's work inside its own worktree at finish.** This is the better
end state and its advocate made the stronger structural case: `head_oid == base_oid` in the
common case (`result.rs:167-169`), so it carries no signal, and committing would make
`changed_paths` a durable base->head diff instead of mutable working-tree state. But its own
advocate identified the disqualifying risk honestly: `commit_result_at`'s
`if p.tree_id() == tree_oid { return Err("nothing staged to commit") }` guard would then
fire on **every** commit-after-Keep. Trading a broken Undo for a broken Commit is not a
trade worth making at the end of a pass. Recorded as the right next step, with the guard
named as the thing to rewrite first.

### Known limit, recorded rather than hidden

The comparison is path-and-status, not content. A person editing a file the agent already
changed leaves the set identical and is not detected. Closing that needs the agent's work
committed so a content diff has something to compare against -- i.e. the option above.
Written into the code comment at the check itself, not only here.

### Copy

The refusal message was also the one place the word "worktree" reached a user -- in an
error, about a thing they had never been shown. It now names files in "the agent's copy of
your project", leads with "Nothing was thrown away" (the refusal is the safe outcome and
should read like one), and calls out new files specifically, since those are the ones with
no saved version to go back to.

## F21 (P1, fixed) - agent worktrees piled up with no way to reclaim the space

The same shape as the Undo bug, found by looking for it deliberately: `canCleanup` has been
computed in `resultActionAvailability` since results shipped, `agent_result_cleanup_worktree`
is registered and bound -- and **no component ever read either**. Every agent run left a
full checkout on disk that the app could not remove and never mentioned.

Wired into the result panel, offered only after Commit or Undo because the backend refuses
before then. That refusal is correct and stays: cleanup is gated on `Committed` or
`Discarded`, states where the agent's work genuinely has landed or been thrown away, so
remaining dirt really is unaccounted for. `explainCleanupOutcome` covers all eleven
outcomes.

## An audit of the whole class

The recurring defect across six passes is a capability built, typed, tested and never
called. A sweep of all 60 registered agent commands found 8 with no frontend caller:

| Command | Verdict |
| --- | --- |
| `agent_result_cleanup_worktree` | Real gap. **Fixed above.** |
| `agent_config_recent_operations` | Added this pass; the Agent Setup panel to show it is real UI work and is **not** done. Recorded rather than rushed. |
| `agent_session_record_conflict` | Not a gap -- its own doc says it is called by the integration step and exposed "for tests and for a future integration-runner caller". |
| `agent_result_find_orphaned` | Not a gap. **This corrects an older doc claim.** The startup scan the docs said was "registered but never called" is the `_all` variant, and it IS wired: `useOrphanResultReconciliation` calls it and is mounted at `AgentDeskView.tsx:452`. The single-session command is its per-session sibling. |
| `agent_result_build`, `agent_result_message_trailers`, `agent_session_attach_context`, `agent_session_graph_view`, `agent_session_propose_graph` | Not audited in depth this pass; recorded as the remaining candidates for the next one. |

Worth keeping the sweep: it is a cheap, repeatable check that catches exactly the class of
bug that has dominated these audits, and it found one real gap plus one stale doc claim in
a single run.

### DECISION -- the plan-edit gap: build removal, keep prose for everything else

Settled with competing sub-agents. Both argued honestly, both conceded ground,
and the decisive facts were verified independently before ruling.

**Verified from both sides:**

- `agent_session_start_graph` takes only `session_id`, reads `proposed_graph`
  off the lead's record and re-validates it (`agent_graph.rs:553-638`). It never
  receives a graph from the frontend, so **trimming a helper needs no change to
  Start** -- only a command that mutates the persisted proposal.
  `agent_session_use_solo_instead` (`:2897`) is a working precedent for exactly
  that write.
- `validate_graph` (`graph.rs:154-212`) has six error variants and **none about
  path adequacy or overlap**. `UnknownDependency` does catch a deleted
  depended-on helper, so removal has a safe floor. But narrowing `allowedPaths`
  below what a job needs is caught by nothing at Start: `check_path_allowance`
  (`policy.rs:395-415`) refuses at tool-call time, **mid-run**, after turns have
  been burned.
- A revision message re-plans with the full transcript including the previous
  proposal (`agent_desk.rs:1364-1377`, `:1818-1833`), so "drop the verifier, the
  builder can run the tests" re-derives budgets, completion conditions and
  dependency edges coherently. A form that deletes a row does one of those four
  things and silently skips the rest.

**The ruling.** Removal is safe and prose is not a substitute for it: the
`UnknownDependency` floor means a bad removal fails loudly at Start, and the
vision's "nothing lands automatically" is undercut by a screen whose only
options are approve-all or discard-all -- especially since that screen grants
the enforced write boundary and cannot narrow it by one agent.

But the prose advocate is right that **editing paths or roles is a different
question with a much worse failure mode** (mid-run refusal, invisible at
approval time), and right that the model re-derives a coherent plan in a way a
form cannot. So:

- **Build:** per-helper Remove, pruning dangling `depends_on` edges, one
  command mirroring `use_solo_instead`.
- **Do not build:** editing `allowedPaths`, roles or completion conditions in
  the card. Those go through revision, where the whole plan is re-derived.
- **Defer:** per-helper provider. `ProposedHelperJob` carries no provider field
  at all (`graph.rs:44-61`); `launch_helper` discovers transport per worktree.
  The build advocate said plainly this half of its own case was weak, and it
  is.

**Done this pass regardless of the ruling:** F114, seeding the composer with the
plan on Revise. Both advocates independently identified the empty box as a real
cost, which made it the one change worth making before the larger decision.

### F119 -- A file permission a person approved could never match (fixed)
