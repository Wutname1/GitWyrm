## `spec_return.rs` -- three defects, one root cause (`d405ec1`)

OpenSpec integration is the vision's "defining advantage", and its promise is
specific: *"GitWyrm updates the exact OpenSpec task."* This file builds the
instruction that tells a spec what an agent did. It had never been audited.

The root cause: `build_return_context` took a pre-picked
`Option<&ResultRecord>` and had **no way to say which execution it was
reporting on**. The caller picked one -- `results.last()`.

### 1. The draft described a different execution than the one under review

`AgentGraphPanel` renders one review panel per execution, and
`ResultReviewPanel` selects its record by `executionId`. But `sendBackToSpec`
passed only `sessionId`; `executionId` was in scope on the very same line and
simply not sent.

So the backend fell back to `results.last()`, which is not even "newest":
`upsert_result` preserves an existing entry's position and appends only new
ones, so `last()` is "whichever execution first wrote a record most recently".

**A person reviewing helper A's three files pressed "Tell the spec" and got a
draft describing helper C's work.** It reads as plausible because it is real
work from the same session -- the wrong slice of it. The module's own doc
claims "a model that exaggerated what it did cannot make the file list say
so", which is true and worth nothing when it is the wrong model's list.

### 2. The button's own precondition was enforced on the wrong side

`canTellSpec` gates the button on `kept || committed`, with a comment
explaining exactly why: *"a result that was still being reviewed -- or one the
person had explicitly thrown away with Undo -- could still be written back
into the spec as though it had proved something. The spec is the project's
source of truth, and it is the one place a mistake outlives the session."*

That gate runs in the window, against the panel's record. The backend acted on
a different one and never read `ResultState` at all. Undo a run, keep the
next, and the discarded work could be the one drafted into the spec.

A rule about what may reach the spec has to hold where the spec is reached.
`ReturnRefusal` gained `WasThrownAway` and `StillBeingReviewed`, both with
plain sentences, and the state check now lives in the backend.

### 3. The account and the file list could come from different executions

`closing_account` scanned `session.messages` unscoped. `SessionMessage`
carries `execution_id` and it was never read, so one execution's file list
could be presented under another's prose beneath the header *"What it said
about the work"* -- two true halves assembled into an account that never
happened, in text the person is invited to save into the spec.

All three are closed by one change: `build_return_context` now takes the whole
result set plus the `execution_id` under review, and uses the already-existing
`result::find_result`. Each defect has a test, and all three were verified to
fail against the old behaviour.

**What was sound, recorded so it is not re-derived:** this module writes
nothing (the drafter returns a draft, the person saves); archived-change
handling is real and correctly ordered *before* the paid AI call; the
read-modify-write-defaults-to-empty pattern from an earlier finding was fixed
here and the fix holds; and wrong-*line* identity in `tasks.md` is handled
elsewhere by content-based relocation, not by this file.

## `execution_registry.rs` -- one finding disproved, one real (`7ada4ec`, `59a08d3`)

### A disproved finding worth keeping the tests from

A review argued, at length and plausibly, that Stop could not reach the audit
phase that runs after an agent finishes: `notify_one` stores one permit, the
working turn's loop consumes it, and its branch is then disabled -- so the
audit's own `cancelled()` would wait forever.

Written as tests, that is **not what happens**. A cancel raised while nobody
is waiting is *kept*, so a second Stop reaches the audit immediately. The
reasoning was believable and nothing had been checking it, so the tests stay.

They also pin the property that genuinely is fragile: one cancel wakes exactly
one waiter. That is correct today only because `run_task` awaits the audit
after its loop has ended. If those phases ever overlap, a single Stop would
reach only one of them -- and now a test says so.

This is the second pass running where a confident argument about another part
of the system turned out to be wrong. The rule that keeps holding: **write it
as a test before believing it, in either direction.**

### `complete()` claimed to be called exactly once; it is not

Two call sites reach it -- the spawned task's own ending, and the watchdog for
when that task panics. They are mutually exclusive today by nothing stronger
than "a panic skips the first", and a task *cancelled* rather than panicked
would reach both. The code handles it safely; the claim was the defect, and
the kind that stops the next person checking. Now pinned by a test.

### Registry concerns checked and found sound

- **Lock discipline**: every method takes the mutex, does a pure map
  operation, and drops it before returning. `wait_for_stop` scopes its guard
  before any `.await`, so the `std::sync::Mutex` is never held across a
  suspend point. `stop()` calls `cancel()` under the guard, but that is a
  non-blocking notify on a different object.
- **Key collisions**: `(SessionId, ExecutionId)` tuple keys, with cross-session
  and cross-execution isolation both already tested.
- **Stop targeting**: cannot hit the wrong execution -- the caller filters by
  scope and persisted state before any `stop()` call.
- **Registration leak**: `register()` has no RAII guard, so the invariant
  rests on nothing fallible sitting between it and the `spawn`. That is true
  today. Left as-is deliberately: a `Drop` guard means restructuring the
  ownership model, which is a larger change than this pass should make on a
  hazard with no live instance. Recorded here so it is a decision rather than
  an oversight.

## Note on method

Every fix this pass was verified by reverting it and watching the new test
fail. Two of the three audit findings that arrived were partly or wholly
wrong -- one disproved outright, one whose severity was in the claim rather
than the code -- and both were caught by the same step.

Worth stating plainly for the next pass: **a sub-agent's finding is a lead,
not a fact.** The value is in what survives verification, and this pass's
best outcome (the wrong-execution draft) came from a finding whose *other*
two thirds needed correcting before use.
