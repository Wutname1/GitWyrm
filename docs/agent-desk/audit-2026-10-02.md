## A deleted allowlist that had only moved (`41f2fdf`)

Every value under `headers` is meant to be secret. The module says why in a
comment on `HISTORICALLY_KNOWN_SECRET_HEADERS`: a four-name allowlist was
removed because "a name is not evidence of what a value holds", and a bearer
token under `X-Auth-Key` or `X-Session` had produced no warning and been shown
unredacted.

`walk` matched it as `path == "headers"` -- an **exact top-level** key. One
level down, header values fell through to the generic recursion and were judged
by `NAMED_SECRET_MARKERS` alone. So `remote.headers.Authorization` was caught
only because "auth" is a substring of its name, and `remote.headers.X-Session`
was not caught at all.

The allowlist had not been deleted. It had moved one nesting level down, where
every test used a top-level `headers` and nothing looked.

Three predicates, three shapes, in one function:

| field | predicate | reaches |
|---|---|---|
| `env` | `path == "env" \|\| path.starts_with("env.")` | top level and below `env.` |
| `headers` | `path == "headers"` | top level only |
| `args` | `leaf == "args"` | any depth |

`args` was already right, and `leaf` was already computed on the line above.
Both others now match by leaf, guarded on the value being an object.

## Is the shape real

GitWyrm never writes it: every `Transport::Remote` arm in `connector.rs` puts
`headers` directly in the entry, and `parse_transport` only reads it there.

But `find_secret_fields` runs in `build_item` on `extra` taken **straight from
the file**, before any normalisation -- and a nested `headers` is not in
`MODELLED`, so `Connector::parse` drops it into `passthrough` and it is copied
**verbatim**. The value really is written out. This module exists to read files
GitWyrm did not write.

## What the debate settled

The narrow side made the stronger empirical case -- no writer, no parser and no
fixture produces a nested `headers` -- and then conceded in its own
counter-argument: nothing stops a person hand-writing one, "no fixture shows
it" describes GitWyrm's writers rather than users' files, and the asymmetry
runs one way. A masked trace id costs a preview line; a copied bearer token is
unrecoverable.

Its objection survives in the fix. Over-marking is not free: it costs a line of
the disclosure screen and, repeated, the marker's meaning. So the match is on a
header **map**, not on the word -- `headers: ["accept"]` is left alone, and a
test says so.

## A correction to my own framing

I described this as `env` being leaf-matched while `headers` was not. Running
it showed `env` is not leaf-matched either: `remote.env.KEY` missed too, for
its own reason. The gap was that **both** anchored to the top of an entry, and
the fix is one predicate rather than a patch to one case.
