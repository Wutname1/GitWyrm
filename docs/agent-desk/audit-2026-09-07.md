## Carried work, and a correction to how pass 46 described it

Pass 46 recorded six hand-written event payloads outside Agent Desk as
instances of the same defect it had just fixed. Working through them, that
framing was half wrong and worth correcting rather than repeating:

- **Two needed no backend change at all** (`359310b`). `GitProgressPayload`
  and `RepoChangedPayload` were *already* in `bindings.ts` -- they are
  reachable from command signatures. The defect was purely that two files
  hand-wrote a second copy of a type that was sitting there ready to import.
  I began by adding `.typ::<>()` registrations for them, checked whether they
  had actually been missing, found they had not, and reverted that half.
  Registering an already-exported type is a no-op that would have read as
  necessary forever after.
- **The real drift was inside one of them.** `GitProgressPayload` carries
  five fields; `RepoPickerModal` declared two. A working consumer
  (`useLocalGitProgress`) imported the full type a few files away. So the app
  held two definitions of one shape, one complete and one stale, with the
  correct example beside the broken one. Nothing is visibly wrong today --
  clone leaves `completed`/`total` as `None` -- but only one of the two copies
  would have noticed a change.
- **Three cannot be fixed here and are recorded in the check itself**:
  `UpdateProgress` uses `u64`, and specta refuses to export a 64-bit integer
  (confirmed by trying it: `export_bindings` fails outright);
  `AiResolveProgress` and `AiCommitProgressPayload` lacked the `Type` derive;
  `settingsSync`'s payload has no Rust counterpart at all, so there is nothing
  for it to drift from.

`eventPayloadContract.test.ts`'s `ROOTS` now covers the cleared files, and its
scope note states each remaining exception with its reason rather than listing
them as outstanding work.

## The commit-progress union (`adf2325`)

Following the `AiCommitProgressPayload` thread found a live defect rather than
a drift risk. `emit_progress` took `kind: &str`; the dialog narrowed the same
field to a seven-value union and looked each value up in an icon table **with
no fallback**. `progressIcons[unknown]` is `undefined`, and `<Icon />` on an
undefined component throws -- so adding a step in Rust and forgetting the
dialog would not fail anywhere at build time, and would then take the window
down mid-run, while it was writing commits.

`kind` is now an enum, the union is generated, and the seven values are one
list. Confirmed by adding an eighth variant: the build now fails naming the
missing icon.

## New ground: `session_recovery.rs`

742 lines, 25 inline tests, never examined by 46 prior passes. It decides what
happens to a chat that was mid-run when the app was killed. Four findings,
all verified against code before acting.

### The two recovery paths disagreed (`3c602c2`)

Agent Desk reconciles abandoned work in two places: lazily when a chat is
opened (`reconcile_executions`) and in a sweep at startup
(`recover_orphaned_executions`). Both answer the same question -- is this
waiting on a person, or on a process that is gone? -- and they had drifted.

The sweep skips two durable human-waits: a recorded merge conflict, and a
lead holding a `proposed_graph` awaiting Start. Its own doc says "Failing
either would throw away the pending choice." The lazy path skipped only the
conflict.

So **opening a chat whose plan was awaiting approval voided that plan**, and
did it invisibly: `AgentGraphPanel` finds the awaiting lead by
`proposed_graph` alone, so Start/Revise/Use-solo still render, while
`Interrupted` is terminal (`graph.rs:421`) and Start does nothing. A visible
control that cannot work is the Rule #1 failure, and it is "nothing lands
automatically" breaking in the direction that costs work.

One line to fix. The more useful output is the test: rather than pinning the
proposal case on the lazy path, `both_recovery_paths_protect_the_same_human_waits`
runs *both* functions over the same records and fails if they disagree. The
existing coverage was asymmetric in exactly the place the code was, which is
how this survived 46 reviews.

### Stopping a lead does not stop its helpers (`9e5b632`)

The startup sweep read only sessions whose header was in a live state,
justified in a comment: "the header mirrors the lead's state, and a helper
only runs while its lead does." Verified false. `stop_execution_at` with
`StopScope::One` stops exactly one execution and then sets the header to
`Stopped` regardless (`agent_desk.rs:2180`), while siblings stay `Working`;
`advance_graph_after_helper_completion` finishes the header the same way.

Kill the app there and the sweep skipped the session. Those helpers'
worktrees -- holding real uncommitted work -- were never inspected, never got
a result, never got a note. The lazy path does not rescue them either: by
design it never looks at a worktree. The work sat on disk with no route to
Keep or discard, which is precisely what the sweep exists to prevent.

The filter now also admits any session that ever started a graph
(`graph_started_at`, set once and never cleared). Sessions that never ran one
are still skipped, so the common case stays one index load.

**The selection rule had no test at all** -- every startup test called
`recover_orphaned_executions_at` directly, bypassing the filter, which is how
a false premise survived in a comment. It is now extracted as
`startup_sweep_should_read` and tested on its own.

### "Stopped when the app closed" was not always true (`50b74db`)

`SessionState::Failed` arrives two ways: the agent failed while GitWyrm
watched (`bridge.rs:483`), or GitWyrm found the work abandoned and wrote that
state itself. `runStoppedBadlyLabel` collapsed `failed` and `interrupted` into
one sentence claiming the app had closed.

For a real failure that is a definite claim about a cause GitWyrm never
observed, and it points at the wrong fix -- restart, when the answer is in
what the agent said before it stopped. The function's own docstring already
makes this argument for `missingSource` and then stopped one case short of
applying it.

### A doc comment sending maintainers to the wrong file (fixed in `9e5b632`)

`INTERRUPTED_REASON`'s comment said the frontend copy lives in
`ConversationPane.tsx`. It lives in `agentDeskResult.ts`; the component only
calls `runStoppedBadlyLabel`. The string appears in `ConversationPane.tsx`
only inside a comment explaining that it was deliberately moved out. A
maintainer following the pointer finds no string and concludes the constant is
dead -- defeating the one job the comment exists to do.

## Checked and sound

Recorded so the next pass does not re-derive them:

- **Process liveness / recycled PIDs.** No PID is consulted anywhere. Liveness
  is a `HashMap` membership test on `(session_id, execution_id)` in an
  in-process registry that starts empty each launch, so PID recycling is
  structurally impossible. No Windows-specific behaviour.
- **`ended_at` left `None` after interruption** -- correct and honest; a
  synthetic end time would fabricate precision.
- **Terminal states are never rewritten** by either path, and idempotency
  across launches is genuinely pinned.
- **`output_summary` guard** correctly refuses to overwrite an agent's real
  summary with recovery boilerplate.

## Note on method

All five fixes were verified by reverting the fix and watching the new test
fail with the expected message. That step has now caught a wrong detector, a
wrong gate, a shadowing hazard, and two false premises stated confidently in
comments across three passes.

The recurring lesson is narrower than "comments lie": **an assertion about
another part of the system is the one most likely to be wrong**, because
nothing recompiles when the other part changes. Both false premises this pass
("a helper only runs while its lead does", "the frontend copy lives in
ConversationPane") were of exactly that shape.
