## Release blockers

### P0 - an event can reach the wrong chat

`RunSessionLinks` is keyed by repository, so linking a second session for the same repo
overwrites the first. Routing then resolves the destination from `event.repo_id`; an unknown
execution can even be created inside whichever session currently owns that repo link.

Required outcome: map execution ID to session ID, unlink only that exact mapping, and test
simultaneous lead/helper traffic in separate sessions for one repository.

### P0 - read-only is advisory when the provider does not ask

The runtime policy rejects a write `PermissionRequest`, but the provider launches with only
shell and URL denied. Provider allow rules can suppress permission requests, bypassing the
handler. Review and Summarize run against the current checkout.

Required outcome: deny write at provider launch for every read-only operation and Plan before
Start, retain the handler as defense in depth, and prove a dirty checkout is byte-identical
under remembered/global allow rules.

### P0 - graph integration targets and reads the wrong thing

The lead integration path uses the session repository path, which is the user's open
checkout, rather than a dedicated lead worktree. Helper change discovery compares the base
tree to HEAD, ignoring ordinary staged/unstaged helper work. Helpers have no production
commit tool, so tests that manually commit do not model the shipped path.

Required outcome: create a dedicated lead integration worktree and calculate each helper's
real worktree delta from its recorded base, including staged, unstaged, and committed work.

### P0 - integration loses file operations and bytes

The current copy path reads files as UTF-8 text and uses an empty string for missing paths or
read errors. It cannot faithfully represent delete, rename, binary, symlink, executable-bit,
or other mode changes and can turn a failure into an empty file.

Required outcome: integrate typed repository operations with byte and mode fidelity. Pause
visibly and recoverably on failure; never report a partial operation as Finished.

### P1 - source clicks do not all do what they say

Automatic start is gated on write authority, so Review and Summarize create a session but do
not run. Kickoff provider overrides are passed into session creation, then automatic start
uses no override; session creation does not durably carry mode/team/provider into the run.

Required outcome: every explicit source action starts immediately, while authority controls
capabilities. Carry the selected or configured provider, mode, and team into the first run.

### P1 - Plan can write before Start

Production sends `started=true` to every run. Plan's proposal turn therefore receives write
authority before the user accepts the graph.

Required outcome: proposal runs use `started=false` and hard write denial. Start is a visible,
durable authority transition, not merely a graph-state label.

### P1 - Finished is not a combined graph result

Graph completion uses completed-node counts as a substitute for a lead review. The
conversation result is tied to the active lead execution, commonly the earlier Plan run,
rather than a combined integration worktree.

Required outcome: serialize helper integration, run a lead review/check over the combined
tree, build one primary result, link helper-scoped results, then and only then mark Finished.

### P1 - completion and recovery actions are unwired

The OpenSpec completion hook has no consumer. Request revision changes state but does not
append guidance or start a turn. Orphan-result detection is registered but not called at
startup. A losing solo-start race can provision a worktree and return without cleaning it.

Required outcome: wire exact-task acceptance, real revision execution, automatic startup
reconciliation, and transactional losing-start cleanup.

## Required build sequence

1. Execution-addressed routing and provider launch authority.
2. Dedicated graph integration worktree and real worktree delta.
3. File-operation fidelity, durable conflict/restart behavior, and atomic/resumable apply.
4. Combined lead review/check and combined result.
5. One-click source execution and kickoff choice persistence.
6. OpenSpec acceptance, revision, and recovery wiring.
7. Automated regression suite, then the full native acceptance matrix.

No later step may weaken the isolation, explicit landing, or visible-response rules to make
an earlier gate easier to pass.
