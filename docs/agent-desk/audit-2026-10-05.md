# Agent Desk audit, 2026-10-05 (pass 75)

Recorded against `agent-desk-openchamber-audit-0f40fb` at `4aabfb2`.

Pass 74 queued two leads. This pass took the older one: **"a check's
`passed` is self-reported"**, carried unchanged since pass 64 and named ten
times. Ten passes described it as a trust gap. It is not a trust gap. It is a
feature that has never once worked, and destroys work when used.

## Automated baseline

Verified before any change, and after the commit:

- `npm run typecheck`: passed.
- `npm run test:unit`: 82 files, 1,225 tests (unchanged -- backend pass).
- `cargo test --lib`: 1,683 passed (now 1,684), 0 failed, 10 ignored.

## The finding was under-described for ten passes (`4aabfb2`)

`CompletionCondition::ChecksPass { command }` is offered to the lead by its
own prompt, in both Plan and Auto mode, with a warning attached: a helper
that does not meet its condition "is reported as unfinished and its work is
NOT merged." A test pinned that offer.

`judge` evaluates it against `ResultCheckOutcome`s from
`checks_for_execution`, which re-reads `RunStep::Check` rows out of the
transcript.

**Nothing in production ever writes a `RunStep::Check`.** It appears only in
tests, in `airun/scripted.rs` (the demo), and in consumers. The single live
tool-call path -- `airun/cli_run.rs`'s `Incoming::ToolCall` arm -- maps every
tool call to `RunStep::Activity`.

So the list is always empty, `matching.is_empty()` always fires, and the
verdict is always:

> It was asked to make "cargo test" pass, but it never ran that check.

`enforce_completion_condition` then sets the helper to `Failed`, writes that
sentence into the chat, and `return`s **before** integration. The work is
dropped.

Any lead that follows its own instructions destroys its helper's work. Not
"unverified" -- inverted. A helper that ran the check and passed is failed
for it.

## Why the interface being careful made it worse

`AgentGraphPanel` renders this well: `stoppedBadly` switches the heading from
"Output" to "Why it stopped" and colours it red, precisely so a failure
cannot read as a success. The panel is doing its job. It states, legibly and
confidently, something that is not true -- which is the trust-in-state rule
inverted rather than merely unmet.

## What the debate settled

One agent argued for synthesising `RunStep::Check` from ACP tool-call data;
the other for withdrawing the condition. **The synthesis side conceded in its
own closing**, and the concession decided it:

- ACP's `status: completed` describes the **tool call's lifecycle**, not the
  command's exit code. A shell tool that runs `cargo test`, gets exit 101,
  and hands the output back has completed successfully *as a tool call*.
  Neither agent could show ACP mandates exit-code propagation.
- A met condition is **silent and merges**. So mapping `completed` to
  `passed: true` would turn today's loud, safe failure into a quiet, unsafe
  one: a red build merged with GitWyrm's assurance.
- `Incoming::ToolCall { title: String }` carries only a title. Codex
  subscribes to `item/started`, which fires *before* the tool runs; the
  Claude adapter classifies `tool_use` (the request) and never
  `tool_result`; the ACP adapter treats `tool_call` and `tool_call_update`
  identically and drops `toolCallId`, so an outcome could not be tied back to
  its call. The signal is not merely unparsed -- for two of three backends it
  is not subscribed to.

Both sides then named the same fix, and it is the one that shipped.

## The fix

- The lead is no longer offered `checksPass`; both instructions now forbid it
  by name and say why. A condition the backend cannot evaluate must not be
  advertised.
- The empty-list branch now distinguishes its two meanings. `checks` empty
  means GitWyrm saw nothing; `checks` non-empty but non-matching means the
  helper ran others and not this one. Only the second is the helper's
  conduct. Still refused either way -- **this is deliberately not a
  loosening**; nothing lands on a guess -- which is exactly the stance the
  `FilesChanged` arm twenty lines below already takes for an unreadable
  worktree. That arm was the model for the sentence.

Verified by reverting the branch and watching both new tests fail, including
the graph-level one, which proves the wording reaches the summary the person
reads.

## Note on method

**A finding carried unchanged is a finding nobody re-derived.** "A check's
`passed` is self-reported" is true, and it describes a *weakness in a working
feature*. The feature does not work. Ten passes restated the sentence from
the prior audit doc rather than asking what writes the field -- one grep,
which is what finally moved it.

**The losing side's concession was the verdict.** As in passes 70 and 72, the
deciding fact came from the side that lost, arguing honestly against itself.

## Still open

`updated_at`, F4, F7's framing question, F8, F9, three hand-written payloads,

**Newly named, not carried from pass 64:** GitWyrm has no channel by which an
agent's check outcomes reach it. `ChecksPass` is now correctly withdrawn
rather than silently broken, but the capability behind it is genuinely
absent, and "make the tests pass" is the most natural thing a lead says. The
honest next step is a real outcome channel -- an exit code parsed from tool
result content -- not a status word. Until then the auditor
(`agentdesk/auditor.rs`), which reads the diff rather than the narration, is
the only real verification in the path.
