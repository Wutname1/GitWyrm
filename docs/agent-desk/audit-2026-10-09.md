## The carried item was already decided -- and its reasoning had one gap

`commands/agent_import.rs` defines `NO_RECORDED_DATE` and
`imported_session_updated_at`, which swaps the sentinel for the import time so
an undated chat does not render as "56y" in the sidebar. Its doc explicitly
declines the Option refactor: seventeen substitution sites across four
adapters, versus one boundary "where the value stops being an adapter's
internal placeholder and becomes text a person reads."

That decision is sound and stands. **But the premise is one word wrong.** It
is not the one boundary. Each adapter sorts its own listing newest-first on
that same string. String-compared, the sentinel falls below every real
RFC 3339 date. So the placeholder escapes into **position** -- a second
output channel, upstream of the guard, in a picker that renders no date at
all, which means ordering is the only date signal a person gets and it is
unlabelled.

Scoped precisely: three sorts, and nothing else. OpenCode orders in SQL by its
real column and never sees the sentinel.

## The fix, and the one that lost (`69d6691`)

Undated rows now sort into their own bucket -- after every dated row because
they have no date, not because of the date they were given -- and by title
among themselves. `updated_at` stays a `String`; no substitution site, type,
or binding changes. The constant moved to `adapters/mod.rs` so the adapters
and the import boundary share one name instead of 27 loose literals.

**I built the losing option first.** A file-mtime fallback is the obvious fix,
and the Codex adapter has shipped exactly that for a long time, which read as
the codebase having already decided. I implemented it across the other two
adapters, hoisted the Codex copy into a shared helper, wrote a test, and
falsified it successfully.

Then the second sub-agent found two things I had not:

1. **It would silently defeat the guard.** `imported_session_updated_at`
   recognises "no date" by comparing against the sentinel. Feed it an mtime
   and the comparison stops matching -- the sidebar takes the mtime instead
   of the import time. The existing test still passes, because it calls the
   function directly with the sentinel and never runs the adapter path.
2. **It split list from read.** `summarize_session` would return an mtime
   while `read_session` still returned the sentinel: the same conversation,
   two different dates, depending which function you asked.

Both verified against the code before acting. The whole mtime change was
reverted, including the Codex behaviour, which is left exactly as it was.

The argument that survives is about honesty, not mechanism. A file mtime is
rewritten by a restored backup, a sync client, or copying the folder to a new
machine -- which is often precisely what somebody has just done when they go
looking for their old chats -- and it arrives as a plain `String`
indistinguishable from a date the transcript really recorded. That trades a
loud unknown for a quiet, plausible falsehood.

## A test of mine that proved nothing -- the fifth in this sequence

The headline test built its list from ordinary dates and asserted the undated
row came last. It passed with the fix removed, because a 1970 sentinel sorts
last under the old rule anyway. Ordering alone cannot tell the two rules
apart.

The case that can is a **recorded date before 1970** -- real, and
string-compares below the sentinel, so the old comparator ranked it beneath a
conversation GitWyrm knew nothing about. Rewritten around that, both tests
fail when the comparator is reverted.

## Note on method

**Build the losing option to find out it loses.** The mtime fix looked
settled, had a shipped precedent, and passed its own falsification. What
killed it was a consequence two files away that no test covered.

**A precedent is evidence about one adapter, not a decision.** "Codex already
does this" carried real weight and turned out to be the weakest link.

**A test built only from typical inputs cannot separate two rules that agree
on typical inputs.** Reach for the input where they disagree.
